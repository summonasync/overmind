# CONTEXT — Overmind System Design

Living description of the system **as built**. Update it when structure, roles, or communication rules change; per-decision rationale lives in `TECHNICAL-SOLUTIONS.md` (ADRs), per-feature history in `BACKLOG/`.

## What Overmind is

A win/mac/linux desktop app (.NET 10) that gives AI coding agents (Claude Code, Kimi Code, Codex, Gemini CLI, Antigravity, Qwen Code) a shared, persistent context store. One local app holds projects, notes/decisions, gates, guards, and skills as the single source of truth; agents connect through a thin stdio MCP adapter over a loopback HTTP API; skill-kits are materialized into project folders so agents pick them up natively. Setup is download-and-run; the only optional external dependency is a local Qdrant (Docker) for semantic search.

## Process topology

```
AI agent (Claude/Kimi/...)                Browser
      | stdio JSON-RPC                         |
      v                                        v
Overmind.Mcp (console adapter)  ----HTTP---->  Overmind.Host (single process)
                                               ├─ Kestrel minimal API, 127.0.0.1 only
                                               ├─ static SPA hosting (web/out)
                                               └─ Avalonia TrayIcon (no native windows)
                                                       |
                                                       v
                                          Overmind.Infrastructure
                                          ├─ SQLite (WAL) + FTS5  — always on
                                          └─ Qdrant (Docker)      — optional, vector search
```

- **One process owns everything.** The Host is the single source of truth; UI, MCP adapter, and future integrations all talk to its HTTP API. No direct DB access from any other process.
- **Single instance.** `SingleInstance` takes a machine-wide lock at startup; a second launch reads the port file and opens the running UI in the default browser instead of starting.
- **Tray-only UX.** The Host has no native windows — an Avalonia `TrayIcon` (FluentTheme) on a dedicated UI thread (STA on Windows; StatusNotifierItem over D-Bus on Linux) offers Open/Quit. The browser is the app window. Quit stops Kestrel cleanly; `--no-tray` runs headless. The folder picker behind `system/browse-folder` shells out per OS: PowerShell FolderBrowserDialog (Windows), `osascript` (macOS), `zenity`/`kdialog` (Linux).
- **Pinned content roots.** Host and MCP adapter both pin their content root to the install dir (`AppContext.BaseDirectory`), not the caller's cwd — launching either from a big repo tree used to inotify-watch the whole tree (BACKLOG/015: 43k host watches when spawned from `$HOME`). Caller's cwd no longer matters; adapters can be spawned from any repo at ~zero inotify cost. Linux smoke guard: `build/watch-guard.sh` (host < 100, adapter < 25 watches).

## Projects and roles

### `src/Overmind.Core` — domain, zero dependencies

Entities, enums, and abstractions only. No framework usings, no EF, no serialization attributes. Everything else points at it.

- Entities: `Project`, `ContextEntry`, `SkillFile`, `Tag`, `EntryTag`, `EntryVersion`, `SkillKit` (origin: `SourceKind`, `SourcePath`, `ImportedAtUtc`; `MarkBundled` stamps a bundled origin without `ImportedAtUtc`, `ForkToManual` is the one-step bundled→manual conversion), `SkillKitEntry` (import bookkeeping: `ImportedContentHash`, `RelativePath` from kit root), `ProjectKit`, `AppSetting`, and the planning domain: `PlanningFeature`, `PlanningArtifact`, `PlanningArtifactVersion`, `PlanningMaterializedFile`, plus the import-facing `FrontmatterKey` (frontmatter key registry: unique case-normalized name → palette hex color, seeded with the ceremony + Mindlash keys, unseen keys auto-register with a deterministic palette color).
- Enums: `EntryType` (note, decision, gate, guard, skill), `AgentPlatform` (claude, kimi-code, codex, gemini, antigravity, qwen), `KitSourceKind` (manual, imported, bundled), planning: `PlanningFeatureStatus` (draft, ready, in-progress, done), `PlanningArtifactKind` (spec, plan, task, result), `PlanningArtifactStatus` (draft, validated, todo, in-progress, review, done, blocked), `PlanningReviewLevel` (light, hard), `PlanningMaterialization` (inherit, off, on, archive), `HumanValidationOverride` (unset, on, off).
- Abstractions (`Abstractions/`): `IEmbeddingProvider`, `IMaterializer`, `ISemanticSearch`, `IPlanningMaterializer`, plus their DTOs (`MaterializationReport`, `DriftItem`, `EntrySearchHit`, `PlanningMaterializationReport`, `PlanningDriftItem`) and exceptions (`MaterializationException`, `PlanningException` carrying `PlanningFailureKind`/`PlanningFailureCode`).
- Domain behavior lives on entities where practical: factory methods (`ContextEntry.Create/CreateSkill`, `ProjectKit.Create`), invariants (`SkillKit.AddEntry` duplicate guard), versioning (`ContextEntry.UpdateContent` snapshots an `EntryVersion`). `PlanningLog` appends dated lines to a planning artifact's `<log>` section.

### `src/Overmind.Infrastructure` — persistence, search, materialization

References Core only.

- `Persistence/` — `OvermindDbContext` (EF Core Sqlite), migrations, `WalPragmaInterceptor` (WAL mode on every connection), design-time factory.
- `Search/` — `FtsSearchService`: FTS5 over all textual entry content, kept in sync via hand-written SQL triggers in the initial migration. Always available, zero dependencies.

Bundled lifecycle services: `BundledSeedService` (boot seed + upgrade sync, see "Skill-kits and materialization"), `BundledManifest` (strict `TryLoad` of `bundled/manifest.json` — IO/JSON failures return false, never throw), `BundledKitForkService` (edit-fork hook invoked by the entries update handler).
- `Planning/` — application services for the planning APIs, extracted per the vertical-slice ADR trigger (006/A1): `PlanningFeatureService`, `PlanningArtifactService`, `PlanningPolicy`, and `PlanningMaterializer` (real `IPlanningMaterializer`, scoped; writes `BACKLOG/<slug>/` + the managed `BACKLOG.md` block per project strategy off/on/archive, archive root injected from Host — replaces the `NullPlanningMaterializer` placeholder from tasks 02–04). Plus the `BacklogImporter` (idempotent file→DB import behind the Host's `--import-backlog` CLI flag; parsing only, writes go through `PlanningFeatureService.ImportAsync`) and the shared `PlanningServiceGuard` (unique-violation detection + swallow-and-log materialization wrappers used by both services). Plus the `FrontmatterKeyRegistry` (scoped; `GetOrRegisterAsync` case-normalizes a key name and returns its color + isNew, seeding the curated ceremony/Mindlash keys on first use — the backlog importer's task-02 fidelity layer consumes it).
- `Configuration/` — `AppSettingsService` over the `AppSetting` table, with `SettingKeys`/`SettingDefaults`.

Contracts (`Api/Contracts/`), validators (`Api/Validation/`), entity→DTO mappers (`Api/Mapping/`), `HttpErrors` (ProblemDetails helpers), `PlanningErrors` (PlanningException → ProblemDetails), `KitImportErrors` (KitImportException → ProblemDetails).
- Tray/lifecycle at project root: `TrayApplication`/`TrayApp` (Avalonia STA loop), `SingleInstance`, `PortFile`, `OvermindPaths` (`~/.overmind`: `overmind.db`, `host.port`; plus `BundledDirectory` — `bundled/` next to the app binary), `OvermindPorts` (default 4761, free-port fallback), `BrowserUri` (rewrites the bound loopback URL to `overmind.localhost` when opening the browser).

### `src/Overmind.Mcp` — stdio MCP adapter (standalone)

References **no other project** — a deliberate decoupling: the adapter is a thin HTTP→JSON-RPC proxy that deserializes Host DTOs via tolerant `JsonElement` reads. Contract is additive-only (see ADR). Console exe, assembly name `overmind-mcp`, built on the `ModelContextProtocol` C# SDK. Spawned by agents via their standard MCP config; exits with code 2 and a stderr hint if the Host API is unreachable at startup.

**Self-registration: `overmind-mcp install`** (feature 009). Intercepted before the host health check, so it works with the Host down. File-based upsert (never agent CLIs): only the `overmind` key is written, unknown keys/tables survive, timestamped `.bak` before the first mutation, re-run converges to `unchanged`. Flags: `--all` (default = detected agents only), `--agents <csv>`, `--project` (git-root scope instead of user-global), `--remove`, `--dry-run`. Exit codes: 0 ok / 1 any failure / 2 usage. The registered command path prefers the stable install link `~/apps/overmind/mcp/overmind-mcp` when it resolves to the running binary, so registrations survive version upgrades.

### `web/` — Next.js 16 static-export SPA

App Router, React 19, TypeScript strict, Tailwind 4, React Query 5, FSD layering. Built with `output: "export"` into `web/out/`, served by the Host from the same origin — there is **no Next.js server in production**, so all data access is client-side React Query over same-origin `/api` (see ADR "static-export SPA data access"). Brand/design reference: `web/brand-book.md`. Slices: entries, kits, projects, search, settings, health, planning (board + feature workspace).

## Communication rules

1. **Loopback only.** Kestrel binds `127.0.0.1` — default port 4761 with free-port fallback; override via `Overmind:BindUrl` config. No auth in v1; loopback binding is the security boundary (token auth is a P2+ candidate). Never bind a public interface without a new ADR.
2. **Port discovery via port file.** On startup the Host writes the bound port to `~/.overmind/host.port`. Consumers resolve the base URL in order: `OVERMIND_API_URL` env var → port file → default 4761. Single-instance relaunch uses the same file to find the running UI.
3. **The HTTP API is the only contract.** UI and MCP adapter never touch the DB, filesystem materialization, or Qdrant directly. Everything goes through `/api/*`. A distinction the domain gates on (agent vs human) is carried by the route prefix — `/api/agent/*` — never by a header or body parameter a caller could omit; see ADR "Two HTTP doors for one aggregate".
4. **API shape.** JSON, camelCase, enums as camelCase strings. Errors as RFC 7807 ProblemDetails (`HttpErrors`); validation failures as 400 `ValidationProblem`. Domain conflicts (overwrite-blocked materialization, second kit activation, DiskPath change while active) are 409 with an explanatory `detail`.
5. **Host↔MCP contract is additive-only.** New fields allowed; renames/removals forbidden (known hazard tolerated while single-repo — a Host DTO rename silently breaks the adapter).
6. **SPA routing.** Static export = one `.html` per route. The Host rewrites extension-less non-`/api` GET paths to `<path>.html` before static files, then falls back to `index.html`. Web root: `OVERMIND_WEB_ROOT` env var, else the pack layout `../web` beside the binary, else the nearest `web/out` walking up from the binary (dev checkout).
7. **The MCP adapter bypasses the system proxy.** `OvermindApiClient` builds its `HttpClient` with `SocketsHttpHandler { UseProxy = false }` (`src/Overmind.Mcp/OvermindApiClient.cs:57`) — loopback is the security boundary, and a system proxy would carry Host traffic off-machine (see ADR, from `audits/audit-2026-09-10.md` BLOCKER-1). Infrastructure embedding providers deliberately keep proxy support: their base URLs (Ollama, OpenAI-compatible) may be remote.

## MCP server design (adapter surface)

Transport: stdio JSON-RPC via the ModelContextProtocol SDK. Server name `overmind`; server instructions tell agents to call `overmind_onboard` first, then read `overmind://` resources.

- **Tools** (`OvermindTools`): `list_projects`, `list_entries` (optional type filter), `read_entry`, `write_entry`, `update_entry` (content-only, title/tags preserved), `search` (`mode=fulltext|semantic`, semantic returns "vector search unavailable" when Qdrant is down). **Write scope is restricted to note/decision/gate/guard** — skills carry files and are managed via the UI until P2 runtime delivery; attempts to write a skill get an explanatory MCP error.
- **Planning tools** (`OvermindPlanningTools`): `planning_list_features`, `planning_read_feature`, `planning_current_task` (read-only), `planning_create_feature`, `planning_upsert_artifact`, `planning_set_status` (empty log note rejected client-side — status moves are recorded in the artifact log), `planning_append_log`, `planning_validate` (gated: a 409 from the human-validation gate reaches the agent verbatim as an error starting with `STOP:`), `planning_set_current` (pins/unpins the board's current feature; pinning one unpins any other). All planning calls go to the agent door `/api/agent/planning/*` only. There is no planning tool to update or delete a feature body — an agent correcting a feature body mid-ceremony currently falls back to a raw HTTP `PUT` on the human door (recorded in BACKLOG hardening).
- **Onboarding tool** (`OvermindOnboardingTools`): `overmind_onboard` (no args) — posts the adapter's cwd to `POST /api/onboard` (or the `OVERMIND_PROJECT_ID` guid override, for symlinked/worktree layouts where the resolved cwd differs from the registered project path) and returns the project id, board summary and the host's quickstart text verbatim; server instructions tell agents to call it first.
- **Resources** (`OvermindResources`), custom scheme `overmind://` (see ADR — renamed from `ctx://`):
  - `overmind://projects`, `overmind://projects/{id}` — JSON.
  - `overmind://projects/{id}/{gates|guards|notes|decisions|skills}` — concatenated markdown (`# Title` + body per entry).
  - `overmind://entries/{id}` — single entry as markdown.
- **Planning resources** (`OvermindPlanningResources`): `overmind://projects/{id}/planning/features` (board as markdown), `…/features/{slug}` (full feature: body + `## Spec`/`## Plan`/`## Tasks`/`## Result`), `…/features/{slug}/current` (current task, or a first-line `STOP:` / `NOTHING TO DO:`).
- **Prompts** (`SessionBootstrapPrompt`): session-bootstrap prompt teaching the agent to read gates/guards at session start and to run the planning loop (board → `current` → obey a STOP → report via `planning_set_status`/`planning_append_log`).
- **Error mapping:** 404 → `ResourceNotFound` protocol error; unreachable API / 503 semantic-down / other statuses → `McpException` with a human-readable message.

## Skill-kits and materialization (v1 mechanics)

Source of truth is the DB; **disk is a managed cache**. Agents load skills only from the filesystem, so activation writes native skill directories into the project folder.

- A `SkillKit` is a named, versioned set of entries (skills, gates, guards), linkable to projects many-to-many via `ProjectKit`. Every kit carries an origin: hand-made (`manual`), imported from a local folder (`imported`, with `SourcePath` and `ImportedAtUtc`), or `bundled` (seeded from the distribution's `bundled/` folder — `SourcePath` into the archive, no `ImportedAtUtc`).
- **Exactly one kit active per project** (ADR): activating a second kit returns 409 instructing to deactivate first; the UI offers a switch flow.
- **Import is a snapshot into the DB** (ADR): a folder is parsed once into ordinary entries — FTS, versions, materializer and drift work unchanged, and the folder is disposable afterwards. Scan (`KitScanner` behind `POST /api/kits/import/scan`) is read-only and side-effect-free: candidates are the scanned folder itself plus each top-level subdirectory that directly contains skills/gates/guards; a skill under a platform directory from `platforms.json` becomes a per-platform variant, any other skill is platform-agnostic; `gates/*.md`/`guards/*.md` at a candidate root become gate/guard entries; broken files surface as per-file preview issues and never abort the scan. Commit (`POST /api/kits/import`, the `KitImportApi` slice) is one transaction per selected kit with per-kit reports — selections match candidates by `relativePath` (root candidate `""`), and a failing kit (name collision, re-import-flagged candidate) rolls back alone. Imported entries land in the find-or-create "Kit Library" project, which the project-delete guard protects (409 while the project owns kit-linked entries); `SkillKits.Name` has a unique index with migration-time dedup.
- **Re-import updates in place** (ADR): a three-way diff per entry on `ImportedContentHash`, matched by the skill's path from kit root persisted as `SkillKitEntry.RelativePath` (candidate prefix stripped at commit; rows predating the column fall back to `{skillsDir}/{title}` reconstruction; gates/guards match by title — the Overmind-owned H1/filename convention). File unchanged since import → keep local edits; entry unchanged since import → take the file as a new `EntryVersion`; both changed → conflict: the entry is refused, local content and the old hash are kept; new files → new entries; files gone → kit-owned entries removed. `POST /api/kits/{id}/reimport` returns the report; a missing source path is a typed 409; `POST /api/kits/{id}/clear-source` flips the kit back to `manual`. Both refuse a bundled kit with typed 409s (`BundledReimportBlocked`, `BundledSourceProtected`): refresh for bundled kits is upgrade-sync's job, and the exit from bundled is edit-fork or delete.
- **Bundled lifecycle: boot seed + upgrade sync (003a).** `BundledSeedService` runs at Host startup right after migrations, before the API accepts requests, over `bundled/` next to the binary (`manifest.json`: `bundleVersion` + kit folder names). Empty library + no `BundledSeedVersion` `AppSetting` → every manifest kit imports through `KitImporter` in bundled mode, then the flag is stamped. A non-empty flagless library is `LibraryInUse` and stamps nothing — a library that later empties still seeds; the once-guard is the stamped flag, so deleting all kits never resurrects the bundles. When the manifest `bundleVersion` exceeds the stored version, upgrade sync adds missing kits, refreshes untouched bundled kits through the three-way diff (origin preserved via `MarkBundled` restamp, `ImportedAtUtc` stays null; a stale `SourcePath` from a relocated install is repointed first), and skips manual/imported kits with colliding names; the new version is stamped even when some kits fail — recovery is the next bundle bump, not a boot retry-loop. Every failure (missing/corrupt manifest, per-kit import errors) is swallowed and logged; boot never breaks because of bundles (ADR).
- **Bundled edit-fork.** The first content edit of an entry owned exclusively by a bundled kit converts the kit in place to `manual`: `BundledKitForkService` on the `EntriesApi.Update` path calls `SkillKit.ForkToManual()` (kind/path/`ImportedAtUtc` cleared in one step), staged on the tracked kit and persisted by the handler's existing save — entry update and fork commit in one transaction, so upgrade sync can never see a saved edit on a still-bundled kit. Entries shared with another kit mutate directly (no fork — the 003a exclusion); title/tag/skillfile-only updates never fork. A forked kit is `manual` by construction, so later upgrade syncs leave it alone.
- Activate = `SkillMaterializer.MaterializeAsync`: for each platform found in the kit's skill files, writes `<native-skills-dir>/<skill-slug>/<file-relative-path>` plus a generated `overmind-bootstrap/SKILL.md` (points agents at `overmind://projects/<id>/gates` and `/guards`, inlines current gates/guards). <!-- removed 2026-09-16 — the sentence covered only platforms explicitly present in the kit's skill files; platform-agnostic files (null `SkillFile.Platform`, shipped with 002) now expand further, see next sentence --> A platform-agnostic skill (null-platform `SkillFile`) expands to **every** platform directory in `platforms.json`, frontmatter passing through byte-identical (spike verdict: no per-platform transforms). Every written file gets a `MaterializedFile` row with a SHA-256 of normalized (LF, UTF-8 no BOM) content.
- **Overwrite protection:** a target path that exists on disk but is not tracked for this kit → 409 `OverwriteBlocked`. Writes run in a DB transaction; on failure, already-written files are best-effort deleted.
- Deactivate removes tracked files, prunes now-empty directories up to the project root, and deletes the rows. `DetectDrift` compares on-disk hashes against rows (Missing/Modified).
- **Project `DiskPath` is immutable while any kit is active or any `MaterializedFile` rows exist** (ADR) — dematerialize resolves relative paths under the current DiskPath, so retargeting mid-flight would delete foreign files. `PUT /api/projects/{id}` returns 409.
- **Web surface (kits slice):** "Import from folder" on the kits page (OS folder picker → scan-preview dialog with candidate checkboxes, editable names, per-kit issues, re-import flags → per-kit import report); origin badges in the kit list and detail (`imported` with path/date, `manual` neutral, `bundled`); the kit-detail source section with Re-import (update report, conflict rows visually distinct) and clear source behind a confirm. Bundled kits get a hint line ("Edits fork this kit into your personal copy.") and neither Re-import nor Clear-source — both are dead ends for the origin. Import has no MCP surface.
- Known debt (BACKLOG hardening): materialized skills land double-nested (`<kit-slug>/<skill-slug>/SKILL.md`); single-level layout decision pending — changing it means adjusting materializer + drift hashes. Codex skills dir unverified for current Codex (`platforms.json` maps `.codex/skills`; official docs list `.agents/skills` locations — deferred P1).

## Distribution (portable)

003a ships Overmind as self-contained portable archives — download, unpack, run. There is no installer package yet: MSIX/pkg is 003b, blocked on a Windows/macOS build host or CI (ADR).

- **Pack.** `build/pack.sh --version <x.y.z> --bundle-version <int> [--crew-kit <path>] [--rids <list>]` — shell-only, repo-hosted, runs on the Linux dev host. Cross-publishes Host and MCP adapter self-contained per RID (default `win-x64,linux-x64,osx-x64,osx-arm64`), always rebuilds the web static export, stages the bundled-kit snapshot (`crew`: `agents/`, `skills/`, `CLAUDE.md`, `SKILLFLOW.md`, `SOCIAL_DICTIONARY.md` — curated allowlist, runtime state excluded, staged read-only) plus `manifest.json`, and writes `dist/overmind-<version>-<rid>.zip|.tar.gz` with a SHA-256 sidecar per archive. `dist/` is gitignored; `build/` is committed.
- **Archive layout.** One top folder `overmind-<version>-<rid>/`: `host/` (self-contained Host, `host/bundled/` with the kit snapshot + `manifest.json` next to the binary), `mcp/` (self-contained `overmind-mcp`), `web/` (static export), `run.sh`/`run.cmd` (launchers that pin `OVERMIND_WEB_ROOT` to the archive's `web/` — the default content-root-relative resolution points outside a self-contained layout), `install.sh` (unix) / `install.ps1` (win).
- **Install = unpack + optional autostart.** `install.sh` registers XDG autostart (`~/.config/autostart/overmind.desktop`) on Linux or a per-user LaunchAgent (`~/Library/LaunchAgents/app.overmind.host.plist`, RunAtLoad; the `launchctl bootstrap` command is printed, not run) on macOS; `install.ps1` drops a Startup-folder shortcut (best-effort — not run-verified from Linux). `--unregister` removes the registration. Scripts write nothing outside the install dir + autostart registration; uninstall = delete the app folder, `~/.overmind` is untouched (cleanup is manual, documented).
- **Upgrade = replace the folder.** No app auto-update: download and unpack the next archive (user data lives in `~/.overmind`, untouched by the swap). A `bundleVersion` bump in the new archive's manifest is what drives the bundled-kit upgrade sync at first boot — the version is monotonic by convention (a lower version silently skips sync, a pack-time parameter).
- **Verification posture.** Linux is smoke-verified end to end (`build/smoke.sh <archive>`: unpack to a temp HOME, boot headless, `/api/health` + seeded crew kit + web UI served, clean shutdown). win/osx archives are build-verified only — cross-publish from Linux, sidecar checks, forbidden-path scan; their autostart specifics may need a fix-forward from 003b.

## Planning (the ceremony as an entity)

Features, specs, plans, tasks and results live in the database as versioned artifacts with markdown+XML bodies; agents and the human UI drive the same aggregate. The database is the source of truth — the `BACKLOG/` folder on disk is a per-project materialized view (or an internal archive), never an input the app trusts.

- **Model** (`Core`): `PlanningFeature` (slug unique per project, body, status draft/ready/in-progress/done, version) and `PlanningArtifact` (kind spec/plan/task/result, one status enum with a per-kind vocabulary, task review level light/hard, `Order`, body, `FrozenAt`, body history in `PlanningArtifactVersion`). Editing a validated artifact requires a dated change note, snapshots the old body, and resets the artifact to draft — the frozen lifecycle is enforced on the entity, not in handlers.
- **Two doors, one aggregate.** The human/UI door is `/api/projects/{id}/planning/*` + `/api/planning/*`; the agent door is `/api/agent/planning/*`, the only surface the MCP adapter calls. Both map onto the same `internal static` handlers and the same `Infrastructure/Planning` services, so "one service path" holds by construction. The agent door exists for the validation gate: when the effective gate is on, the agent's `validate` returns 409 `HumanValidationRequired` with a `STOP:` detail and `current` reports a stop state, while the UI's validate always works (ADR "Two HTTP doors for one aggregate").
- **Gate resolution** (`Infrastructure/Planning/PlanningPolicy`): global settings `planning.requireHumanValidationDefault` and `planning.materializationDefault` (both default `off`) with per-project overrides (`unset/on/off`, `inherit/off/on/archive`); effective values are exposed and set via `GET|PUT /api/projects/{id}/planning/workflow` and mirrored in Settings + project pages in the UI.
- **Materialization.** `on` writes `BACKLOG/<feature-slug>/{feature,spec,plan,result}.md` + `tasks/NN-<slug>.md` into the project repo and maintains a managed block in the repo's `BACKLOG.md` between `<!-- overmind:planning:start/end -->` markers: hand-written content outside the markers is preserved byte-for-byte, and the tracked hash covers the block content only, so human index edits never read as drift. A target file that exists but is untracked → 409 unless `force` adopts it; tracked files are rewritten freely (a hand edit of a tracked file is transient — the next ceremony mutation rewrites it from DB truth; `force` gates only the adoption of foreign untracked files), and drift (Missing/Modified) is reported, never auto-repaired. `archive` writes the same layout under `<data dir>/projects/<project>/backlog/` with free rewrites; `off` deletes what was tracked. Every delete path is hash-guarded: a file is removed (or its managed block stripped) only when its normalized SHA-256 — block-only for `BACKLOG.md` — matches the tracked row, so foreign content sitting at a tracked path in either root is kept and surfaced as a report warning. A failed or refused sync never rolls back the DB write — problems surface as report warnings. Documents render with exactly one leading H1: `# Feature NNN — <title>` on feature.md and `# Spec|Plan|Result NNN — <title>` on the artifact documents, derived from the feature title; the task document keeps its own title heading (task filenames are generated from it). Artifact bodies are stored H1-free, so a legacy body carrying 2–3 duplicated leading H1s normalizes back to exactly one on the next sync (self-healing) — the import → materialize → re-import cycle is byte-stable.
- **Importer.** Host CLI `--import-backlog <repoRoot|BACKLOG>` (optional `--project <id|name>`, else the single project whose `DiskPath` matches) parses frontmatter + XML bodies into features and artifacts; idempotent by `(ProjectId, Slug)` / `(Kind, Order)`, one transaction per feature, run-and-exit — the process imports against the SQLite store and exits 0/non-zero without booting the web host (no Kestrel, no tray, no `host.port` write), duplicating the stdout report to a file with `--report <path>` (UTF-8 no BOM, parent dir must exist). After the summary line the CLI prints every `report.Skipped` entry on its own line (prefixes `skipped:` / `ignored:` / `unknown status` / `reassigned:` / `matched:`), then the `NewKeys` (`new key: name (color)`), `Preserved` (`preserved:`) and `CreatedFallbacks` (`created:`) lists and the `NextStep` line, so nothing drops silently. Frontmatter token values are stripped of inline comments (first ` #` to end of line) before parsing; the legacy spec/plan status `approved` maps to `validated` (its historical FROZEN meaning), and `result.md` imports as a `result` artifact at order 0 with the shared `{draft, validated}` document statuses — the import → materialize → re-import round-trip is closed. Letter-suffixed task filenames (`01b-*.md`) are accepted: the base digits give the order, and on a collision the file first folds into an existing task artifact with identical log-stripped content (`matched:` report entry — keeps import → materialize → re-import a no-op for the leftover suffixed file) or otherwise appends at max+1 ascending by letter with a loud `reassigned:` report entry; task files that still don't parse are skipped. Document bodies are stored canonical and H1-free: the leading `# Feature NNN — …` / `# Spec NNN — …` heading is stripped on parse (the materializer re-derives the canonical heading from the feature title when writing, and collapses a task body's duplicated leading headings to its single title heading, which task filenames are generated from), so re-importing a materialized repo reads as no change. Declared losses: `requirements.md` and the `BACKLOG.md` index are not read back, `amended:` frontmatter lines and the text after a `validated:` date are dropped (the date itself survives), the text of a document's leading H1 is dropped for feature/spec/plan/result (re-derived from the feature title on materialize), unknown `status` values still import as the kind's default, and task files without an `NN[-letter]-` prefix are skipped.
- **MCP planning surface**: nine tools (`planning_list_features`, `planning_read_feature`, `planning_current_task`, `planning_create_feature`, `planning_upsert_artifact`, `planning_set_status`, `planning_append_log`, `planning_validate`, `planning_set_current`) and three markdown resources (`overmind://projects/{id}/planning/features`, `…/features/{slug}`, `…/features/{slug}/current`); the bootstrap prompt teaches the loop board → current → obey STOP → report.

## Storage, search, embeddings

- **SQLite (WAL)** at `~/.overmind/overmind.db` is the only metadata/document store. Migrations in Infrastructure, applied at Host startup. Entities: projects, entries, skill files, tags, entry versions, kits, kit links, project-kit links, materialized files, app settings, and the planning tables (`PlanningFeatures`, `PlanningArtifacts`, `PlanningArtifactVersions`, `PlanningMaterializedFiles`, `FrontmatterKeys` — unique NOCASE `Name`, migration `20260908173101_Planning` for the planning set, `20260919164533_AddFrontmatterKeyRegistry` for the registry). Kit import added the origin/bookkeeping columns and the unique kit-name index across four migrations: `20260914134204_KitOrigin`, `20260914151947_SkillFileAgnosticPlatform`, `20260915120341_UniqueKitName` (dedupes duplicate names before creating the index), `20260916083250_SkillKitEntryRelativePath`. 003a added no migration — the bundled-kit seed state is the existing `AppSetting` key `BundledSeedVersion` (bundle version as an invariant-culture string, read/written through `AppSettingsService`). `PlanningMaterializedFiles` deliberately has multiple cascade paths (`Project` direct and `Project → PlanningFeature → row`); SQLite accepts that, but a move to SQL Server would require `Restrict` on one path (comment in `OvermindDbContext`).
- **FTS5 always on.** Full-text search over all entry content, maintained by SQL triggers. No degradation path — it is the baseline.
- **Qdrant is the only vector backend, and it is optional.** Local Docker, explicit health check. Down → **honest degraded mode**: semantic search returns 503, UI shows a degraded banner, MCP `search` tells the agent to use `mode=fulltext`, the app never crashes.
- **Embedding provider is pluggable and selected in Settings** (`IEmbeddingProvider`): ONNX local (default; all-MiniLM-class model downloaded on first run into `~/.overmind/models/` with progress — keeps the install small, offline after first run), Ollama (URL-configurable), OpenAI-compatible (URL + key). Changing provider triggers reindexing (`ReindexService`).
- Entry indexing is write-through: the API calls `EntryIndexingService` on create/update/delete; indexing failures must not break CRUD.
