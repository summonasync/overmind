# CONTEXT — Overmind System Design

Living description of the system **as built**. Update it when structure, roles, or communication rules change; per-decision rationale lives in `TECHNICAL-SOLUTIONS.md` (ADRs), per-feature history in `BACKLOG/`.

## What Overmind is

A win/mac/linux desktop app (.NET 10) that gives AI coding agents (Claude Code, Kimi Code, Codex, Gemini CLI, Antigravity, Qwen Code) a shared, persistent context store. One local app holds projects, notes/decisions, gates, guards, and skills as the single source of truth; agents connect through a thin stdio MCP adapter over a loopback HTTP API; skill-kits are materialized into project folders so agents pick them up natively. Setup is download-and-run; the only optional external dependency is a local Qdrant (Docker) for semantic search.

## Process topology

```
AI agent (Claude/Kimi/...)                Browser
      | stdio JSON-RPC                         |
      v                                        v
Overmind.Mcp (console adapter)  ----HTTP---->  Overmind.Host (single process)
                                               ├─ Kestrel minimal API, 127.0.0.1 only
                                               ├─ static SPA hosting (web/out)
                                               └─ Avalonia TrayIcon (no native windows)
                                                       |
                                                       v
                                          Overmind.Infrastructure
                                          ├─ SQLite (WAL) + FTS5  — always on
                                          └─ Qdrant (Docker)      — optional, vector search
```

- **One process owns everything.** The Host is the single source of truth; UI, MCP adapter, and future integrations all talk to its HTTP API. No direct DB access from any other process.
- **Single instance.** `SingleInstance` takes a machine-wide lock at startup; a second launch reads the port file and opens the running UI in the default browser instead of starting.
- **Tray-only UX.** The Host has no native windows — an Avalonia `TrayIcon` (FluentTheme) on a dedicated UI thread (STA on Windows; StatusNotifierItem over D-Bus on Linux) offers Open/Quit. The browser is the app window. Quit stops Kestrel cleanly; `--no-tray` runs headless. The folder picker behind `system/browse-folder` shells out per OS: PowerShell FolderBrowserDialog (Windows), `osascript` (macOS), `zenity`/`kdialog` (Linux).
- **Pinned content roots.** Host and MCP adapter both pin their content root to the install dir (`AppContext.BaseDirectory`), not the caller's cwd — launching either from a big repo tree used to inotify-watch the whole tree (BACKLOG/015: 43k host watches when spawned from `$HOME`). Caller's cwd no longer matters; adapters can be spawned from any repo at ~zero inotify cost. Linux smoke guard: `build/watch-guard.sh` (host < 100, adapter < 25 watches).

## Projects and roles

### `src/Overmind.Core` — domain, zero dependencies

Entities, enums, and abstractions only. No framework usings, no EF, no serialization attributes. Everything else points at it.

- Entities: `Project`, `ContextEntry`, `SkillFile`, `Tag`, `EntryTag`, `EntryVersion`, `SkillKit` (origin: `SourceKind`, `SourcePath`, `ImportedAtUtc`; `MarkBundled` stamps a bundled origin without `ImportedAtUtc`, `ForkToManual` is the one-step bundled→manual conversion), `SkillKitEntry` (import bookkeeping: `ImportedContentHash`, `RelativePath` from kit root), `ProjectKit`, `AppSetting`, and the planning domain: `PlanningFeature`, `PlanningArtifact`, `PlanningArtifactVersion`, `PlanningMaterializedFile`, plus the import-facing `FrontmatterKey` (frontmatter key registry: unique case-normalized name → palette hex color, seeded with the ceremony + Mindlash keys, unseen keys auto-register with a deterministic palette color).
- Enums: `EntryType` (note, decision, gate, guard, skill, tombstone, featureRequest), `AgentPlatform` (claude, kimi-code, codex, gemini, antigravity, qwen), `KitSourceKind` (manual, imported, bundled), planning: `PlanningFeatureStatus` (draft, ready, in-progress, done), `PlanningArtifactKind` (spec, plan, task, result), `PlanningArtifactStatus` (draft, validated, todo, in-progress, review, done, blocked), `PlanningReviewLevel` (light, hard), `PlanningMaterialization` (inherit, off, on, archive), `HumanValidationOverride` (unset, on, off).
- Abstractions (`Abstractions/`): `IEmbeddingProvider`, `IMaterializer`, `ISemanticSearch`, `IPlanningMaterializer`, plus their DTOs (`MaterializationReport`, `DriftItem`, `EntrySearchHit`, `PlanningMaterializationReport`, `PlanningDriftItem`) and exceptions (`MaterializationException`, `PlanningException` carrying `PlanningFailureKind`/`PlanningFailureCode`).
- Domain behavior lives on entities where practical: factory methods (`ContextEntry.Create/CreateSkill/CreateTombstone`, `ProjectKit.Create`), invariants (`SkillKit.AddEntry` duplicate guard), versioning (`ContextEntry.UpdateContent` snapshots an `EntryVersion`). `ContextEntry.CreateTombstone` (029) builds the burial memory: deleting a regular entry through `EntriesApi.Delete` converts instead of erasing — the original row and its versions go, and a `tombstone` entry is born with the original title + «(deleted)», an `Original type:` line, the deletion timestamp, agent/human door + actor provenance (agent door = `X-Overmind-Session` present, actor resolved from the session row), an optional reason (query param on the delete path, door surfaces pending task 02), and the final content preserved verbatim in a fenced block sized past any internal fence; deleting a tombstone is a plain delete (no second tombstone). `PlanningLog` appends dated lines to a planning artifact's `<log>` section; `PlanningSections` (Core root, same rule) owns the anchored-XML-section grammar both `PlanningLog` and the 039 patch path (`PatchSection`/`TickAc`) parse and rewrite through.

### `src/Overmind.Mcp` — stdio MCP adapter (standalone)

References **no other project** — a deliberate decoupling: the adapter is a thin HTTP→JSON-RPC proxy that deserializes Host DTOs via tolerant `JsonElement` reads. Contract is additive-only (see ADR). Mutation tools never echo written bodies back: host responses are projected to compact confirmations (`id`/kind/`status`/`version`/`bodyChars`, plus the appended log line for `planning_set_status` — the host returns an empty 200 on status/log moves, so that confirmation is built from the accepted request); read tools return full payloads. Console exe, assembly name `overmind-mcp`, built on the `ModelContextProtocol` C# SDK. Spawned by agents via their standard MCP config; exits with code 2 and a stderr hint if the Host API is unreachable at startup.

**Self-registration: `overmind-mcp install`** (feature 009). Intercepted before the host health check, so it works with the Host down. File-based upsert (never agent CLIs): only the `overmind` key is written, unknown keys/tables survive, timestamped `.bak` before the first mutation, re-run converges to `unchanged`. Flags: `--all` (default = detected agents only), `--agents <csv>`, `--project` (git-root scope instead of user-global), `--remove`, `--dry-run`. Exit codes: 0 ok / 1 any failure / 2 usage. The registered command path prefers the stable install link `~/apps/overmind/mcp/overmind-mcp` when it resolves to the running binary, so registrations survive version upgrades.

## Communication rules

1. **Loopback only.** Kestrel binds `127.0.0.1` — default port 4761 with free-port fallback; override via `Overmind:BindUrl` config. No auth in v1; loopback binding is the security boundary (token auth is a P2+ candidate). Never bind a public interface without a new ADR.
2. **Port discovery via port file.** On startup the Host writes the bound port to `~/.overmind/host.port`. Consumers resolve the base URL in order: `OVERMIND_API_URL` env var → port file → default 4761. Single-instance relaunch uses the same file to find the running UI.
3. **The HTTP API is the only contract.** UI and MCP adapter never touch the DB, filesystem materialization, or Qdrant directly. Everything goes through `/api/*`. A distinction the domain gates on (agent vs human) is carried by the route prefix — `/api/agent/*` — never by a header or body parameter a caller could omit; see ADR "Two HTTP doors for one aggregate".
4. **API shape.** JSON, camelCase, enums as camelCase strings. Errors as RFC 7807 ProblemDetails (`HttpErrors`); validation failures as 400 `ValidationProblem`. Domain conflicts (overwrite-blocked materialization, second kit activation, DiskPath change while active) are 409 with an explanatory `detail`.
5. **Host↔MCP contract is additive-only.** New fields allowed; renames/removals forbidden (known hazard tolerated while single-repo — a Host DTO rename silently breaks the adapter).
6. **SPA routing.** Static export = one `.html` per route. The Host rewrites extension-less non-`/api` GET paths to `<path>.html` before static files, then falls back to `index.html`. Web root: `OVERMIND_WEB_ROOT` env var, else the pack layout `../web` beside the binary, else the nearest `web/out` walking up from the binary (dev checkout).
7. **The MCP adapter bypasses the system proxy.** `OvermindApiClient` builds its `HttpClient` with `SocketsHttpHandler { UseProxy = false }` (`src/Overmind.Mcp/OvermindApiClient.cs:57`) — loopback is the security boundary, and a system proxy would carry Host traffic off-machine (see ADR, from `audits/audit-2026-09-10.md` BLOCKER-1). Infrastructure embedding providers deliberately keep proxy support: their base URLs (Ollama, OpenAI-compatible) may be remote.

## MCP server design (adapter surface)

Transport: stdio JSON-RPC via the ModelContextProtocol SDK. Server name `overmind`; server instructions tell agents to call `overmind_onboard` first, then read `overmind://` resources.

- **Tools** (`OvermindTools`): `list_projects`, `list_entries` (optional type filter), `read_entry`, `write_entry`, `update_entry` (content-only, title/tags preserved), `search` (`mode=fulltext|semantic`, semantic returns "vector search unavailable" when Qdrant is down). **Write scope: note/decision/gate/guard/featureRequest/tombstone** — skills carry files and are managed via the UI until P2 runtime delivery; attempts to write a skill get an explanatory MCP error. `featureRequest` (079) is the catch-it-when-spoken intake type for product ideas and asks: origin provenance is a convention, not a column — lead the body with `Origin: <session/feature, date>` or carry it in tags; promotion to a board feature stays a ceremony act (no auto-promotion tooling).
- **Planning tools** (`OvermindPlanningTools`): `planning_list_features`, `planning_read_feature`, `planning_current_task` (read-only), `planning_create_feature`, `planning_upsert_artifact`, `planning_patch_artifact` (039: `replace_section`/`tick_ac` without resending the body — see the write-cost model below), `planning_set_status` (empty log note rejected client-side — status moves are recorded in the artifact log), `planning_append_log`, `planning_validate` (gated: a 409 from the human-validation gate reaches the agent verbatim as an error starting with `STOP:`), `planning_claim_feature` / `planning_unclaim_feature` (099: a claim is a hard mutation lock on the feature — reads stay open, foreign-session mutations 409; liveness rides the adapter session, EOF auto-releases), `planning_delete_artifact` (094: soft delete, agents delete draft artifacts only — validated/done deletion is the human door; dependency edges refuse with "clean up dependencies first"), `planning_set_feature_status` (the delegated close hand — done from any non-done status, or inProgress review rollback, ONLY on the user's explicit in-session request; mandatory logNote with provenance recorded as a dated line in the feature log; every other manual matrix move is a typed 400 — human-door only), `planning_materialize_status` (read-only mirror diagnostics over the persisted run report — lastSuccess/lastAttempt, per-file last run, trackedFiles/stalePaths, strategy/targetDir; 074), `planning_export_backlog` (075: renders the full current mirror through the pass's own renderers into a caller-supplied absolute, empty target — the explicit commit-alongside snapshot; zero tracking rows, typed refusals for non-absolute, non-empty, and inside-the-mirror targets). Routine planning calls go to the agent door `/api/agent/planning/*`; two tools deliberately call the human door instead — `planning_set_feature_priority` (it wraps the human `PUT` on the feature) and `planning_materialize` (precedent: the manual materialize trigger since 067). There is no planning tool to update or delete a feature body — an agent correcting a feature body mid-ceremony currently falls back to a raw HTTP `PUT` on the human door (recorded in BACKLOG hardening).
- **Read/write cost model (039 D9, 040 D3).** Eight planning tools are priced and say so verbatim in their descriptions, so tool discovery alone answers "which one do I use". Writes: `planning_append_log` — cheapest write: one dated line, body is not resent; `planning_edit_log` — cheap correction tier: rewrites the text of the newest own-door log line (same-actor-marker precondition, single-line text, version-traced — the original survives in the version trace), body is not resent; `planning_patch_artifact` — middle: replaces one XML section or ticks one AC item, rest of the body untouched (`replace_section` on a missing section is a 400 listing what exists, re-ticking a ticked item is an idempotent no-op, every patch snapshots and bumps `Version`); `planning_upsert_artifact` — most expensive write: resends the full body. Reads mirror the ladder: `planning_read_artifact` with `sections` — cheapest read: only the named sections, absent ones reported in `missingSections` (soft — a read never 400s on a missing section); `planning_read_artifact` without — one artifact, full body; `planning_read_artifact_diff` — cheaper than any full body when only the change matters: two versions of one artifact as a unified diff, omitted pair = the two most recent versions (adjacent log-only bumps legitimately diff empty; a trailing newline is ignored, so 'x' vs 'x\n' diffs as empty — no git-style `\ No newline` marker); `planning_read_feature` — most expensive read: the whole feature with all artifacts. The session-bootstrap prompt carries both pick-by-cost routing lines: line → `planning_append_log`; one section / one AC item → `planning_patch_artifact`; whole body → `planning_upsert_artifact`; one section → `planning_read_artifact` with sections; one artifact → `planning_read_artifact`; whole feature → `planning_read_feature`.
- **Onboarding tool** (`OvermindOnboardingTools`): `overmind_onboard` (no args) — posts the adapter's cwd to `POST /api/onboard` (or the `OVERMIND_PROJECT_ID` guid override, for symlinked/worktree layouts where the resolved cwd differs from the registered project path) and returns the project id, board summary and the host's quickstart text verbatim; server instructions tell agents to call it first.
- **Resources** (`OvermindResources`), custom scheme `overmind://` (see ADR — renamed from `ctx://`):
  - `overmind://projects`, `overmind://projects/{id}` — JSON.
  - `overmind://projects/{id}/{gates|guards|notes|decisions|skills}` — concatenated markdown (`# Title` + body per entry).
  - `overmind://entries/{id}` — single entry as markdown.
- **Planning resources** (`OvermindPlanningResources`): `overmind://projects/{id}/planning/features` (board as markdown), `…/features/{slug}` (full feature: body + `## Spec`/`## Plan`/`## Tasks`/`## Result`), `…/features/{slug}/current` (current task, or a first-line `STOP:` / `NOTHING TO DO:`).
- **Prompts** (`SessionBootstrapPrompt`): session-bootstrap prompt teaching the agent to read gates/guards at session start and to run the planning loop (board → `current` → obey a STOP → report via `planning_set_status`/`planning_append_log`).
- **Error mapping:** 404 → `ResourceNotFound` protocol error; unreachable API / 503 semantic-down / other statuses → `McpException` with a human-readable message.

## Skill-kits and materialization (v1 mechanics)

Source of truth is the DB; **disk is a managed cache**. Agents load skills only from the filesystem, so activation writes native skill directories into the project folder.

- A `SkillKit` is a named, versioned set of entries (skills, gates, guards), linkable to projects many-to-many via `ProjectKit`. Every kit carries an origin: hand-made (`manual`), imported from a local folder (`imported`, with `SourcePath` and `ImportedAtUtc`), or `bundled` (seeded from the distribution's `bundled/` folder — `SourcePath` into the archive, no `ImportedAtUtc`).
- **Exactly one kit active per project** (ADR): activating a second kit returns 409 instructing to deactivate first; the UI offers a switch flow.
- **Import is a snapshot into the DB** (ADR): a folder is parsed once into ordinary entries — FTS, versions, materializer and drift work unchanged, and the folder is disposable afterwards. Scan (`KitScanner` behind `POST /api/kits/import/scan`) is read-only and side-effect-free: candidates are the scanned folder itself plus each top-level subdirectory that directly contains skills/gates/guards; a skill under a platform directory from `platforms.json` becomes a per-platform variant, any other skill is platform-agnostic; `gates/*.md`/`guards/*.md` at a candidate root become gate/guard entries; broken files surface as per-file preview issues and never abort the scan. Commit (`POST /api/kits/import`, the `KitImportApi` slice) is one transaction per selected kit with per-kit reports — selections match candidates by `relativePath` (root candidate `""`), and a failing kit (name collision, re-import-flagged candidate) rolls back alone. Imported entries land in the find-or-create "Kit Library" project, which the project-delete guard protects (409 while the project owns kit-linked entries); `SkillKits.Name` has a unique index with migration-time dedup.
- **Re-import updates in place** (ADR): a three-way diff per entry on `ImportedContentHash`, matched by the skill's path from kit root persisted as `SkillKitEntry.RelativePath` (candidate prefix stripped at commit; rows predating the column fall back to `{skillsDir}/{title}` reconstruction; gates/guards match by title — the Overmind-owned H1/filename convention). File unchanged since import → keep local edits; entry unchanged since import → take the file as a new `EntryVersion`; both changed → conflict: the entry is refused, local content and the old hash are kept; new files → new entries; files gone → kit-owned entries removed. `POST /api/kits/{id}/reimport` returns the report; a missing source path is a typed 409; `POST /api/kits/{id}/clear-source` flips the kit back to `manual`. Both refuse a bundled kit with typed 409s (`BundledReimportBlocked`, `BundledSourceProtected`): refresh for bundled kits is upgrade-sync's job, and the exit from bundled is edit-fork or delete.
- **Bundled lifecycle: boot seed + upgrade sync (003a).** `BundledSeedService` runs at Host startup right after migrations, before the API accepts requests, over `bundled/` next to the binary (`manifest.json`: `bundleVersion` + kit folder names). Empty library + no `BundledSeedVersion` `AppSetting` → every manifest kit imports through `KitImporter` in bundled mode, then the flag is stamped. A non-empty flagless library is `LibraryInUse` and stamps nothing — a library that later empties still seeds; the once-guard is the stamped flag, so deleting all kits never resurrects the bundles. When the manifest `bundleVersion` exceeds the stored version, upgrade sync adds missing kits, refreshes untouched bundled kits through the three-way diff (origin preserved via `MarkBundled` restamp, `ImportedAtUtc` stays null; a stale `SourcePath` from a relocated install is repointed first), and skips manual/imported kits with colliding names; the new version is stamped even when some kits fail — recovery is the next bundle bump, not a boot retry-loop. Every failure (missing/corrupt manifest, per-kit import errors) is swallowed and logged; boot never breaks because of bundles (ADR).
- **Bundled edit-fork.** The first content edit of an entry owned exclusively by a bundled kit converts the kit in place to `manual`: `BundledKitForkService` on the `EntriesApi.Update` path calls `SkillKit.ForkToManual()` (kind/path/`ImportedAtUtc` cleared in one step), staged on the tracked kit and persisted by the handler's existing save — entry update and fork commit in one transaction, so upgrade sync can never see a saved edit on a still-bundled kit. Entries shared with another kit mutate directly (no fork — the 003a exclusion); title/tag/skillfile-only updates never fork. A forked kit is `manual` by construction, so later upgrade syncs leave it alone.

## Planning (the ceremony as an entity)

Features, specs, plans, tasks and results live in the database as versioned artifacts with markdown+XML bodies; agents and the human UI drive the same aggregate. The database is the source of truth — the `BACKLOG/` folder on disk is a per-project materialized view (or an internal archive), never an input the app trusts.

- **Model** (`Core`): `PlanningFeature` (slug unique per project, body, status draft/ready/in-progress/done, version) and `PlanningArtifact` (kind spec/plan/task/result, one status enum with a per-kind vocabulary, task review level light/hard, `Order`, body, `FrozenAt`, body history in `PlanningArtifactVersion`). Editing a validated artifact requires a dated change note, snapshots the old body, and resets the artifact to draft — the frozen lifecycle is enforced on the entity, not in handlers.
- **Dependencies** (030 feature-level, 081 task-level): task-level `blockedBy` declares sibling task orders of the same feature on the task upsert (declarative replace, empty array clears; no separate add/remove tools), an edge closes when the blocker task reaches `done|review`, and `planning_current_task` honors the edges — blocked tasks are skipped for the next actionable one, and when every remaining task is blocked the response stops naming the chain (030 DFS style, cycle-guarded).
- **Two doors, one aggregate.** The human/UI door is `/api/projects/{id}/planning/*` + `/api/planning/*`; the agent door is `/api/agent/planning/*`, the surface the MCP adapter calls for routine planning — two tools are deliberate exceptions and use the human door: `planning_set_feature_priority` (wraps the human feature `PUT`) and `planning_materialize` (precedent: materialize since 067). Both map onto the same `internal static` handlers and the same `Infrastructure/Planning` services, so "one service path" holds by construction. Artifact deletion (094) is split by guard matrix, not by route shape: the agent door exposes `DELETE /api/agent/planning/artifacts/{id}` (`LockToClaim`, draft-only for agents) while the human `DELETE /api/planning/artifacts/{id}` is unrestricted — the guard lives once in the domain (`PlanningArtifact.Delete(byHuman)`), the doors only declare their side. The agent door exists for the validation gate: when the effective gate is on, the agent's `validate` returns 409 `HumanValidationRequired` with a `STOP:` detail and `current` reports a stop state, while the UI's validate always works (ADR "Two HTTP doors for one aggregate"). Feature-status delegation (023/08): the agent door exposes `POST /api/agent/projects/{id}/planning/features/{slug}/status` restricted to `done`/`inProgress` with a mandatory logNote — it validates through the same `PlanningFeatureService` transitions matrix as the human-door `PUT` (typed `InvalidFeatureTransition` whose detail carries the current status), so the matrix itself has a single owner.
- **Gate resolution** (`Infrastructure/Planning/PlanningPolicy`): global settings `planning.requireHumanValidationDefault` and `planning.materializationDefault` (both default `off`) with per-project overrides (`unset/on/off`, `inherit/off/on/archive`); effective values are exposed and set via `GET|PUT /api/projects/{id}/planning/workflow` and mirrored in Settings + project pages in the UI.
- **Materialization.** `on` writes `BACKLOG/<feature-slug>/{feature,spec,plan,result}.md` + `tasks/NN-<slug>.md` into the project repo — the generated `BACKLOG.md` index is retired (049): the board is the only live state copy, and no index row is ever created again. Since 051 the same pass also projects entries to `<DiskPath>/ENTRIES/{type}/{kebab-title}-{id8}.md` — a SIBLING of BACKLOG/, never nested inside it (the backlog importer scans BACKLOG feature folders only). Frontmatter carries id/type/title/tags/createdAt/updatedAt + verbatim body; newline-free title/tags — the plan flattens whatever is stored; tombstone entries from 029 materialize like any type. Entry files are tracked rows like the planning tree: hand edits refuse the pass (033), force warns per file, a deleted entry's file is removed on the next pass, and skill entries get an ENTRIES/skill/ file alongside the kit-owned SkillFile materialization (deliberate v1 duplication — the kit remains the source of truth for skill files). Entries land on the next materialization pass — planning mutations enqueue the async pass, entry CRUD does not, so an entry-only change reaches disk after the next planning mutation or a manual `planning_materialize`. Titles carrying colons/quotes render unquoted (no ENTRIES parser exists; a future reverse import would need a quoting dialect). A pass is atomic plan-then-write (074): the full operation plan (write / skip / refuse per file) is computed before anything touches disk, and any refusal — an untracked file at a planned path, or a tracked file whose disk hash drifted from both the row and the plan — aborts the entire run with a 409 listing every refusal; zero files are written that run. Skips are byte-identical no-ops only (disk already matches the board), never guarded files. Every run start stamps `LastMaterializationAttemptAt` (lastAttempt) while only a fully successful run stamps `LastMaterializedAt` (lastSuccess) and nulls the failure fields; every completed or aborted run persists a per-file report on the project (`LastMaterializationRun` JSON: startedAt/finishedAt/atomic/written/skipped/refused), and a plan-phase abort stamps the attempt + error but persists no report — diagnostics render that as "no report for this attempt", never as stale data. Onboard and `planning_materialize_status` render attempt vs success honestly, and `planning_materialize_status` adds trackedFiles, stalePaths (tracked files the last run neither wrote nor skipped, drift-aware) and strategy/targetDir. `force` flips the guards to overwrite-with-per-file-warnings. Drift (Missing/Modified) is reported, never auto-repaired. `archive` writes the same layout under `<data dir>/projects/<project>/backlog/` with free rewrites; `off` deletes what was tracked. Every delete path is hash-guarded: a file is removed only when its normalized SHA-256 matches the tracked row, so foreign content sitting at a tracked path in either root is kept and surfaced as a report warning. Legacy `BACKLOG.md` rows left by pre-049 builds ride the same machine: the pass strips the managed block (block-only hash — hand-written content outside the markers survives byte-for-byte), deletes the row and never touches the file again; a hand-edited block refuses the pass (033), `force` strips with a per-file warning. A failed or refused sync never rolls back the DB write — problems surface as report warnings. Documents render with exactly one leading H1: `# Feature NNN — <title>` on feature.md and `# Spec|Plan|Result NNN — <title>` on the artifact documents, derived from the feature title; the task document keeps its own title heading (task filenames are generated from it). Artifact bodies are stored H1-free, so a legacy body carrying 2–3 duplicated leading H1s normalizes back to exactly one on the next sync (self-healing) — the import → materialize → re-import cycle is byte-stable.
- **Git discipline for the mirror (075).** Overmind never commits or branches, and the mirror is untracked by default: every materializer pass runs `MirrorGitHygiene` (`Infrastructure/Planning`) — walk up from the materialization write root to the nearest `.git/` directory and idempotently ensure the repo-root-relative `BACKLOG/` + `ENTRIES/` patterns in `.git/info/exclude` (nested targets get a `<prefix>/` form; only `.git` directories count — worktree checkouts keep walking) — file writes only, the Host never executes git. The hook sits in `SyncAsync` after the refusal gate and before the write pass, so the exclude exists before the first mirror file lands; the outcome (`ensured`/`already-present`/`no-repo`/`failed`) rides `PlanningMaterializationReport.GitHygiene` as an additive field on the human-door materialize response (the MCP tool's compact echo drops it — ledger #324), and a hygiene failure never fails the pass. The mechanism is non-breaking for already-tracked repos: exclude entries do not untrack anything, so a repo that has been committing its mirror keeps doing so until a human runs `git rm -r --cached BACKLOG ENTRIES` (the deliberate, user-gated migration). The mirror stays branch-agnostic — the database holds one board per project and every pass rewrites from DB truth — so a checked-out other branch simply shows that branch's `BACKLOG/` state to git; files left behind by another branch read as locally-edited or untracked to the materializer and are skipped with a reason, never silently overwritten, and `force` still deliberately rewrites the mirror onto the current branch when that is the intent. Committing the planning alongside the code is the explicit export door: `POST /api/projects/{id}/planning/export` on both doors / MCP `planning_export_backlog` renders the full current mirror (planning tree + entries projection) through the same renderers the pass uses — byte-identical output — into a caller-supplied absolute, empty target directory and creates zero tracking rows and zero drift machinery (a snapshot, not a second sync); refusals are typed: non-absolute target → 400 `ExportTargetNotAbsolute`, existing non-empty target (a file included) → 409 `ExportTargetNotEmpty`, a target inside `BACKLOG/`/`ENTRIES/` or at the project root → 409 `ExportTargetInsideMirror`, a path-guard escape → 400 `PathTraversal`. Mirror filenames are ASCII-safe: slug generation transliterates Cyrillic first (`CyrillicTransliteration`, GOST 7.79-2000 System B family) and strips remaining non-ASCII, so no octal-escape names reach git; the pin is content-hash-gated — a tracked ENTRIES filename whose stored hash equals the freshly rendered document keeps its path — so existing names stay byte-stable while their titles are unchanged, and a title change is what converges the filename.
- **Importer.** Host CLI `--import-backlog <repoRoot|BACKLOG>` (optional `--project <id|name>`, else the single project whose `DiskPath` matches) parses frontmatter + XML bodies into features and artifacts; idempotent by `(ProjectId, Slug)` / `(Kind, Order)`, one transaction per feature, run-and-exit — the process imports against the SQLite store and exits 0/non-zero without booting the web host (no Kestrel, no tray, no `host.port` write), duplicating the stdout report to a file with `--report <path>` (UTF-8 no BOM, parent dir must exist). After the summary line the CLI prints every `report.Skipped` entry on its own line (prefixes `skipped:` / `ignored:` / `unknown status` / `reassigned:` / `matched:`), then the `NewKeys` (`new key: name (color)`), `Preserved` (`preserved:`) and `CreatedFallbacks` (`created:`) lists and the `NextStep` line, so nothing drops silently. Frontmatter token values are stripped of inline comments (first ` #` to end of line) before parsing; the legacy spec/plan status `approved` maps to `validated` (its historical FROZEN meaning), and `result.md` imports as a `result` artifact at order 0 with the shared `{draft, validated}` document statuses — the import → materialize → re-import round-trip is closed. Letter-suffixed task filenames (`01b-*.md`) are accepted: the base digits give the order, and on a collision the file first folds into an existing task artifact with identical log-stripped content (`matched:` report entry — keeps import → materialize → re-import a no-op for the leftover suffixed file) or otherwise appends at max+1 ascending by letter with a loud `reassigned:` report entry; task files that still don't parse are skipped. Document bodies are stored canonical and H1-free: the leading `# Feature NNN — …` / `# Spec NNN — …` heading is stripped on parse (the materializer re-derives the canonical heading from the feature title when writing, and collapses a task body's duplicated leading headings to its single title heading, which task filenames are generated from), so re-importing a materialized repo reads as no change. Declared losses: `requirements.md` is not read back (the retired `BACKLOG.md` index is neither written nor read since 049), `amended:` frontmatter lines and the text after a `validated:` date are dropped (the date itself survives), the text of a document's leading H1 is dropped for feature/spec/plan/result (re-derived from the feature title on materialize), unknown `status` values still import as the kind's default, and task files without an `NN[-letter]-` prefix are skipped.
- **MCP planning surface**: thirty tools (`planning_list_features` — the full board view, not the work order; `planning_task_queue` — the what's-next projection: the board order IS the queue, priority asc → queue position, first on the board is next in the queue; `planning_move_feature` — five band-scoped moves (up/down/first/last/toPosition), the human reorder door is the dashboard drag; `planning_set_feature_priority` — crosses bands, only on the user's explicit approval; `planning_read_feature`, `planning_list_artifacts` — the metadata-only roster of one feature's artifacts, the cheapest way to see what a feature contains before any body read, every row carrying additive `pointers: [{path, anchor}]` parsed from the body's pointer lines (046); `planning_feature_code` — read-only repo discovery for a feature: worktrees and branches carrying its slug or NNN prefix (126); `planning_update_feature` — partial edit of a feature's title/body/priority with a mandatory logNote — durable what/why stays correctable by agents; status not editable here; `planning_claim_feature` / `planning_unclaim_feature` — the 099 mutation lock: claiming hard-locks the feature's mutations to the holder session, EOF auto-releases; `planning_read_artifact`, `planning_read_artifact_diff` — two versions of one artifact as a unified diff (read-only, alias addressing like `planning_read_artifact`; omitted pair = the two most recent versions, adjacent log-only bumps legitimately diff empty, a trailing newline is ignored), `planning_current_task`, `planning_create_feature`, `planning_upsert_artifact`, `planning_upsert_tasks`, `planning_patch_artifact`, `planning_set_status`, `planning_append_log`, `planning_edit_log` — corrects the text of the newest own-door log line (same-actor-marker precondition, single-line text, version-traced; feature-level logs stay append-only), `planning_validate`, `planning_set_feature_status`, `planning_delete_artifact` — guarded soft delete, draft-only on this door (094), `planning_list_feature_dependencies`, `planning_add_feature_dependency`, `planning_remove_feature_dependency`, `planning_import_feature`, `planning_materialize` — a manual rerun trigger wrapping the materialize endpoint, compact written/skipped echo, a refusing run surfaces the 409 refusal detail as a tool error; `planning_materialize_status` — read-only mirror diagnostics: lastSuccess vs lastAttempt, the persisted per-file run report, trackedFiles, stalePaths, strategy/targetDir; `planning_export_backlog` — renders the full current mirror (planning tree + entries projection) through the pass's own renderers into an explicit empty absolute target directory — the commit-alongside snapshot with zero tracking rows; typed refusals for non-absolute (400), non-empty (409), and inside-`BACKLOG/`/`ENTRIES/`-or-project-root (409) targets; queue positions are DB-only — the materializer and importer ignore them) and three markdown resources (`overmind://projects/{id}/planning/features`, `…/features/{slug}`, `…/features/{slug}/current`); the bootstrap prompt teaches the loop board → current → obey STOP → report, plus the write-cost, read-cost, dependency and queue routing (see "MCP server design").
- **Pointer convention (046).** An artifact body can point at a repo file instead of copying it: a pointer line is a line whose first non-whitespace token is `pointer:` followed by whitespace and a repo-relative path with an optional `#anchor` — `pointer: src/plans/auth-redesign.md#non-goals`. The grammar is strict and case-sensitive (`Pointer` or `pointers:` at line start are not marker lines; a bare `pointer` token missing the colon is a marker and rejects; the anchor binds at the first `#`; no absolute paths, no backslashes, no `..` segments, no spaces — one pointer per line). Artifact write doors (upsert, tasks batch, patch, import bodies) validate marker lines and reject malformed ones with a typed 400 `InvalidPointerMarker` carrying a teaching detail; feature bodies are never write-validated. The read side (`PointerMarkerGrammar.Parse`) is tolerant by design — malformed lines are skipped, never thrown, so reads cannot fail on a body. Pointers are computed-not-stored: `PlanningArtifactResponse` (current-task payload, feature reads, task-batch echoes) and the `planning_list_artifacts` roster rows carry additive `pointers` arrays (empty when none) built at read time from the stored body with zero file I/O — the server NEVER opens the referenced files, and existence/sync checks are out of scope by design; the agent pulls the target with its own file tools only when it decides to.

## Storage, search, embeddings

- **SQLite (WAL)** at `~/.overmind/overmind.db` is the only metadata/document store. Migrations in Infrastructure, applied at Host startup. Entities: projects, entries, skill files, tags, entry versions, kits, kit links, project-kit links, materialized files, app settings, and the planning tables (`PlanningFeatures`, `PlanningArtifacts`, `PlanningArtifactVersions`, `PlanningMaterializedFiles`, `FrontmatterKeys` — unique NOCASE `Name`, migration `20260908173101_Planning` for the planning set, `20260919164533_AddFrontmatterKeyRegistry` for the registry). Kit import added the origin/bookkeeping columns and the unique kit-name index across four migrations: `20260914134204_KitOrigin`, `20260914151947_SkillFileAgnosticPlatform`, `20260915120341_UniqueKitName` (dedupes duplicate names before creating the index), `20260916083250_SkillKitEntryRelativePath`. 003a added no migration — the bundled-kit seed state is the existing `AppSetting` key `BundledSeedVersion` (bundle version as an invariant-culture string, read/written through `AppSettingsService`). `PlanningMaterializedFiles` deliberately has multiple cascade paths (`Project` direct and `Project → PlanningFeature → row`); SQLite accepts that, but a move to SQL Server would require `Restrict` on one path (comment in `OvermindDbContext`). `PlanningTaskDependencies` (081) is a self-referencing cascade pair on `PlanningArtifacts` (`BlockedById` and `BlockingId` both Cascade) — SQLite takes it, SQL Server would reject the multiply-defined cascade path and need `Restrict` on one side.
- **FTS5 always on.** Full-text search over all entry content, maintained by SQL triggers. No degradation path — it is the baseline.
- **Qdrant is the only vector backend, and it is optional.** Local Docker, explicit health check. Down → **honest degraded mode**: semantic search returns 503, UI shows a degraded banner, MCP `search` tells the agent to use `mode=fulltext`, the app never crashes.
- **Embedding provider is pluggable and selected in Settings** (`IEmbeddingProvider`): ONNX local (default; all-MiniLM-class model downloaded on first run into `~/.overmind/models/` with progress — keeps the install small, offline after first run), Ollama (URL-configurable), OpenAI-compatible (URL + key). Changing provider triggers reindexing (`ReindexService`).
- Entry indexing is write-through: the API calls `EntryIndexingService` on create/update/delete; indexing failures must not break CRUD.
