<goal>
Guard the <log> section on the full-body upsert door: planning_upsert_artifact (and the batch door planning_upsert_tasks) must only ever tail-append log lines — never rewrite, reorder, or drop history.
</goal>

<scope>
- src/Overmind.Core/Entities/PlanningArtifact.cs — in UpdateBody, before ApplyBodyMutation: compare PlanningLog.Parse(current Body) vs PlanningLog.Parse(incoming body). The incoming log must contain the stored log lines as an exact ordered prefix; anything else (modified line, removed line, reordered, log section dropped) throws.
- New PlanningFailureCode (e.g. LogHistoryNotAppendable) in src/Overmind.Core/Abstractions/PlanningFailureCode.cs + PlanningException factory with diagnostics: first divergent line index, stored vs incoming line counts, hint to use planning_append_log / planning_patch_artifact. Mirror the PatchLogSectionNotReplaceable pattern.
- src/Overmind.Core/PlanningLog.cs — reuse Parse for the comparison; no new parser. Comparison on parsed PlanningLogLine records (trim-normalized date/text/source) so raw whitespace reflow must not false-positive.
- tests/Overmind.Core.Tests/Entities/PlanningArtifactTests.cs — entity cases: unchanged body passes; pure tail-append passes; no-log → log-added passes; modified historical line fails; removed line fails; reordered lines fails; log section dropped fails.
- tests/Overmind.Infrastructure.Tests/PlanningServiceTests.cs — service door: UpsertAsync with rewritten log fails with the new code; UpsertTasksAsync batch door inherits the same guard.
</scope>

<anti-scope>
- No import-specific handling: re-import (PlanningFeatureService) goes through UpdateBody and inherits the guard as-is — a mirror whose log rewrites stored history gets rejected with diagnostics; that is desired, do not add bypass flags.
- planning_append_log, the patch-door guard (039), status-move log lines, version-diff tooling (045) — untouched.
- Frozen-artifact rules unchanged (logNote still required when frozen).
</anti-scope>

<constraints>
- Guard lives in the entity (UpdateBody), NOT the service layer — all three doors (single upsert, batch upsert, re-import) inherit it through the existing shared path.
- logNote is appended AFTER the guard check (ApplyBodyMutation already appends it post-write) — the guard compares incoming body vs stored body only.
- Follow existing file conventions; no comments; messages in English.
</constraints>

<acceptance-criteria>
- [x] Upsert whose body only tail-appends log lines succeeds (entity test green).
- [x] Upsert that modifies/removes/reorders any stored log line fails with the new failure code and a diagnostic naming the first divergent line (entity test green).
- [x] Batch door planning_upsert_tasks inherits the same guard (service test green).
- [x] Re-import path needs no code change and existing import tests stay green.
- [x] dotnet build green, dotnet test green.
</acceptance-criteria>
