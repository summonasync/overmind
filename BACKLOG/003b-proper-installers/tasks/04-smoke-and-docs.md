# 003b/04 — Installer smoke verification, live install, docs and ADRs

<goal>
`setup.exe` is proven on real Windows — automatically by a smoke script covering install → boot → API/UI/MCP → uninstall → residue, and once by hand through the actual wizard. The repo's documentation stops claiming Overmind has no installer, and both technology decisions are recorded as ADRs.
</goal>

<context>
This closes feature 003b. Tasks 01–03 produced `POST /api/shutdown`, the icons, and `dist/overmind-<version>-setup.exe`. Nothing has verified that the installed application actually runs — and until this feature, no win-x64 build of Overmind had ever been executed at all (`CONTEXT.md:136`: win/osx archives are "build-verified only").

The Linux counterpart is `build/smoke.sh`, which unpacks an archive, boots it under an isolated `HOME`, and asserts health + seeded kit + web UI + clean shutdown. This task writes the Windows equivalent, but the isolation story is different and the difference is load-bearing — read the next section before writing a line of it.

## How isolation actually works on Windows (verified in the code)

Overriding `%USERPROFILE%` does **not** redirect the app's data. `OvermindPaths.DataDirectory` uses `Environment.GetFolderPath(SpecialFolder.UserProfile)`, which on Windows resolves through the shell's known-folder API and ignores the environment variable. What the Host *does* honour:

- **`Overmind__DatabasePath`** (env) → `Overmind:DatabasePath` config, read at `src/Overmind.Host/DependencyInjection.cs:84`. Redirects the SQLite file. Its parent directory is created automatically.
- **`Overmind__PortFilePath`** (env) → `Overmind:PortFilePath`, read at `src/Overmind.Host/Program.cs:169`. Redirects the port file the smoke polls.
- **`OVERMIND_MODELS_DIR`** (env) → model download location (`src/Overmind.Infrastructure/Embeddings/OvermindModelPaths.cs`).
- **`OVERMIND_API_URL`** (env) → how `overmind-mcp` finds the Host (`src/Overmind.Mcp/ApiBaseUrl.cs`); without it the adapter falls back to the real `~/.overmind/host.port`, which would point the handshake at the wrong instance.

Two things stay global no matter what, and the smoke must accommodate rather than fight them:

- `src/Overmind.Host/Program.cs:21` unconditionally creates the real `%USERPROFILE%\.overmind`. An empty directory may appear; that is expected, and the residue check must not treat it as a failure.
- **The single-instance mutex is per-user and global** (`Local\Overmind.Host.<username>`, `src/Overmind.Host/SingleInstance.cs`). If another Host is already running, the smoke's instance **exits with code 0** after trying to open a browser (`Program.cs:36-52`) — it does not error. A naive smoke would then hang waiting for a port file that never appears. So the smoke must detect a running Host up front and refuse with a clear message (or stop it deliberately, which is exactly what the upgrade cell does on purpose).

Executor reads ONLY this file.
</context>

## 1. `build/windows/smoke-installer.ps1 <setup.exe>`

Structure it as explicit cells, each printing a pass line, with a `try/finally` that always uninstalls and removes the temp tree. Exit non-zero with the failing cell named on any failure; print `SMOKE OK: <summary>` at the end.

**Cell 0 — preflight.** Refuse to run if a Host is already live: if `%USERPROFILE%\.overmind\host.port` exists and `GET http://127.0.0.1:<port>/api/health` answers, abort with "a running Overmind was found; quit it from the tray before smoking the installer". Explain the mutex reason in the message. (Without this the later cells fail in a way that looks like an installer bug.)

**Cell 1 — silent install.** Run `& $Setup /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /DIR="$installDir" /TASKS="" | Out-Null` where `$installDir` is a fresh folder under `$env:TEMP`. `/TASKS=""` selects none of the three tasks, so this cell touches neither PATH, nor the Run key, nor the desktop. Inno's silent mode returns before finishing, so wait for `host\Overmind.Host.exe` to exist (poll up to 120 s) instead of trusting the exit alone. Assert the expected tree: `host\Overmind.Host.exe`, `host\bundled\manifest.json`, `host\bundled\crew`, `mcp\overmind-mcp.exe`, `web\index.html`, and assert `run.cmd` and `install.ps1` are **absent**.

**Cell 2 — headless boot in isolation.** Set for the child process only: `Overmind__DatabasePath` = `$work\overmind.db`, `Overmind__PortFilePath` = `$work\host.port`, `OVERMIND_MODELS_DIR` = `$work\models`. Start `host\Overmind.Host.exe --no-tray` with stdout/stderr redirected to files under `$work`. Poll `$work\host.port` for up to 120 s; if the process exits early, print the last 40 lines of both logs and fail — do not wait out the full budget.

**Cell 3 — health.** `GET http://127.0.0.1:<port>/api/health` → HTTP 200 and `status` = `ok`.

**Cell 4 — bundled kit seeded.** `GET /api/kits` → the response contains a kit named `crew` with `sourceKind` `bundled`. This proves `host\bundled\` landed next to the binary where `OvermindPaths.BundledDirectory` looks for it.

**Cell 5 — web UI.** `GET /` → HTTP 200, body contains `<!DOCTYPE html`. This proves `ResolveWebRoot()` found `{app}\web` with no launcher and no `OVERMIND_WEB_ROOT` — the core bet of spec D9.

**Cell 6 — MCP handshake.** Start `mcp\overmind-mcp.exe` with `OVERMIND_API_URL` set to the smoke instance's base URL, write one JSON-RPC line to stdin and read one response line from stdout:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"smoke","version":"1.0"}}}
```

Assert the response parses as JSON with `id` = 1 and a `result.serverInfo` object. Kill the adapter afterwards. Give the read a 30 s timeout so a hung adapter fails the cell instead of the script.

**Cell 7 — graceful stop.** `POST /api/shutdown` → 202; the process exits within 10 s. This exercises the very endpoint the installer depends on, against the real published binary rather than a test host.

**Cell 8 — silent uninstall.** Run `unins000.exe /VERYSILENT /SUPPRESSMSGBOXES` from the install dir and wait for the process to disappear (poll, do not assume synchronous). Assert: install dir gone (or empty), no `Overmind` value under `HKCU\...\Run`, `{installDir}\mcp` absent from both the user and machine `Path`, **and `%USERPROFILE%\.overmind` still present** — a silent uninstall must never delete user data (spec R8). Also capture the user `Path` value before cell 1 and after this cell and assert they are byte-identical.

**Cell 9 — upgrade over a running install.** Install again silently, boot it (isolated as in cell 2), leave it running, then run the same `setup.exe` silently a second time over it. Assert the second install completes, the Host process is gone afterwards (stopped through `PrepareToInstall` → `POST /api/shutdown`, not killed), and the binaries were actually replaced (compare file write timestamps). Uninstall at the end.

**Cell 10 — PATH round-trip with the task actually enabled.** <!-- added 2026-09-21: cells 1-9 all install with `/TASKS=""`, so none of them exercise the PATH write at all — and that code was rewritten during the task-03 fix round (the `[Registry]` entries were replaced by a programmatic `AddPathSegment` in `[Code]`). Without this cell the feature ships its PATH handling unverified. -->

Capture `HKCU\Environment\Path` verbatim. Install silently into a temp prefix with `/TASKS="mcppath"`. Assert: the value now ends with the install's `\mcp` segment, has **no** leading or doubled `;`, and is still of type `REG_EXPAND_SZ` (check with `Get-Item`'s `GetValueKind`, not `Get-ItemProperty`, which hides the kind). Then uninstall silently and assert the value is **byte-identical** to the captured original. Run this cell last, and restore the captured value yourself if any assertion fails — leaving a developer's PATH damaged is not an acceptable failure mode for a test.

A safety net already exists: the controller backed up `HKCU\Environment\Path`, `HKLM\...\Environment\Path` and the `HKCU\...\Run` key to `<session scratchpad>\path-backup\` before this task started. Verified beforehand: neither PATH nor the Run key mentions Overmind, so any Overmind trace you find afterwards is yours.

Note for the `/DELETEDATA` path: do **not** test it against the real profile. Either skip it with a printed note, or exercise it only against a throwaway Windows profile — deleting the developer's `~/.overmind` is unacceptable collateral. State which choice was made in the task log.

**The executor must not run `setup.exe` interactively, must not click through the wizard, must not take screenshots and must not interact with the desktop or tray in any way.** This section is carried out by the user, and the controller folds the reported results into the feature's closing record.

The checklist the user works through — each item recorded as observed or not:

- SmartScreen warning appears (expected — unsigned, spec D1) and the install proceeds past it
- Start Menu entry present with the zergling icon; Installed Apps shows Overmind with a version and the icon
- Tray icon appears; the UI opens in a browser; `~/.overmind/host.port` is written
- A **fresh** shell resolves `overmind-mcp` (a shell open before the install will not see the new PATH — that is normal, note it rather than filing it as a bug)
- Sign out and back in (or reboot) → Overmind starts automatically
- Uninstall through Installed Apps: answer **No** to the data prompt → `~/.overmind` survives; shortcuts, Run entry and PATH segment are gone
- Record whether a console window appears or flashes (the Host is a `Microsoft.NET.Sdk.Web` console-subsystem binary; `runminimized` mitigates but may not eliminate it)

Anything broken here is fixed forward inside this feature; anything merely ugly gets a `BACKLOG.md` hardening line. Because this pass is user-driven and asynchronous, the executor does not wait for it: finish sections 1 and 3, report, and leave the live-pass results for the controller to append.

- **`TECHNICAL-SOLUTIONS.md`** — two ADRs in the existing format (Context / Decision / Alternatives considered / Consequences), dated 2026-09-21:
  1. **Inno Setup over MSIX/WiX/Velopack.** The decisive argument is that MSIX installs into `C:\Program Files\WindowsApps\<versioned-id>\` — ACL-restricted and renamed on every update — so an external agent has no stable path to spawn `overmind-mcp.exe`, which is the adapter's entire delivery model. Plus: MSIX needs signing even to sideload; WiX buys GPO/Intune deployment that a personal tool does not need; Velopack ships the auto-update that 003a rejected. Consequence: building the installer requires Windows, so the Linux host can no longer produce every artifact alone.
  2. **`POST /api/shutdown` as the stop contract.** A windowless tray process cannot be stopped by `WM_CLOSE`, and Restart Manager is unreliable against it; `taskkill /F` on a process holding an open SQLite database is not an upgrade strategy. Loopback remains the only boundary — consequence to state plainly: any local process can stop the Host, which is the same trust model as the rest of the API.
