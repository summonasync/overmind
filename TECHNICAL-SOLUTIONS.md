# Technical Solutions

Architecture Decision Records. Newest first. Once Accepted, changing a decision requires a new ADR that supersedes the old one — never a silent edit.

## Optional kits stack per project, the mandatory kit refuses project activation, and the bootstrap is per-kit (250) — 2026-11-19
**Status:** Accepted (spec 250 R3; supersedes "Single active kit per project", 2026-09-06, and closes its recorded consequence "revisiting multi-kit = new ADR + bootstrap namespacing work")
**Context:** The crew kit splits into six kits (owner ruling 2026-11-18, decision `47b948a3`): `overmind-ceremony` is mandatory and reaches the agent HOME skill dirs through feature 251's door, while `dotnet-crew`, `rust-crew`, `js-crew`, `sociality` and `crew-extras` are optional and attach per project — a fullstack project takes `dotnet-crew` + `js-crew` at once. The 2026-09-06 ADR forbade exactly that: the materializer wrote one shared `overmind-bootstrap/SKILL.md` per platform, so a second activation collided on the same path and returned 409 OverwriteBlocked. Its own text names the way out (per-kit bootstrap namespacing plus a new ADR). Two structural facts made the change cheaper than it looked: `ProjectKit` was always a many-to-many keyed on `(ProjectId, KitId)` with its own `IsActive`, so nothing at the schema level ever said "one"; and the refusal itself lived only inside `KitsApi.Activate`, which STRUCTURE rule 6 rejects for a domain invariant — any second door (the crew→six auto-migration of R5, a future MCP or CLI activation) would have walked straight past it.
**Decision:** Four linked moves. (1) **Stacking is the model.** Activation no longer looks at other active links; several kits may be active for one project, each keeping its own `MaterializedFile` rows keyed by `KitId`, so dematerialize and drift stay per-kit operations — deactivating one kit removes exactly that kit's files and leaves the other's in place. (2) **The bootstrap becomes per-kit.** The materializer writes `<skills-dir>/overmind-bootstrap-<kit-slug>/SKILL.md` per targeted platform, where `<kit-slug>` is `Slug.From(kit.Name, "kit")` (Cyrillic-transliterating, fallback `"kit"`), and the document title carries the kit name (`# Overmind Bootstrap — <kit>`). The body was already kit-scoped — it renders the gates and guards among that kit's own entries — so path and content now agree. (3) **Mandatory is metadata, guarded in the seam.** `SkillKit.Mandatory` (migration `AddKitMandatory`, default false for every existing row) with `SkillKit.EnsureProjectActivatable()` throwing `KitActivationException.MandatoryGlobalKit`; `KitActivationService` is the single production seam for activation writes — it resolves project and kit, calls the domain guard **before** any filesystem work (a refused activation leaves no files and no rows), materializes, then upserts the `ProjectKit` link, and it owns the symmetric `DeactivateAsync` refusal (`NotLinked`) for a kit that is not linked at all. `KitsApi` became a dispatcher that maps the typed exception to ProblemDetails (`MandatoryGlobal` → 409 carrying that title, `NotLinked` → 404) and adds no rule of its own; the R5 crew→six migration is required to drive activation through this same service. The flag is fed by the bundle: `bundled/manifest.json` `kits[]` now accepts objects `{"name": …, "mandatory": bool}` (a bare string still parses as `mandatory: false`, so pre-250 packagers keep working), and `BundledSeedService.ApplyMandatoryFlagsAsync` re-asserts the manifest value after both the fresh seed and the upgrade sync, for `SourceKind == Bundled` kits only. `KitResponse` gains an additive `Mandatory` field — no renames, no removals (Host↔MCP additive-only). (4) **The old layout heals lazily.** Each materialize pass prunes the tracked rows *of the kit being activated* that the new plan no longer covers: the file is deleted, empty parent directories are pruned under the project root, a per-file warning names it, the row is dropped — and rows belonging to other kits are never touched. No path-rewriting migration ships.
**Alternatives considered:** One merged bootstrap listing every active kit — rejected: its content would be a function of the whole activation set, so activating or deactivating any kit rewrites a file no single kit owns, which is precisely the `KitId`-keyed ownership that dematerialize, drift detection and the clobber guard all read. Renaming the shared directory only when a collision is detected — rejected: the same kit would materialize to different paths depending on what else happens to be active, and drift reports churn on every second activation. A migration rewriting pre-250 `MaterializedFile` paths — rejected: the file is regenerated by the next activation anyway, so the lazy prune covers the whole population with no schema work and no risk of deleting a file the pass had not planned. Keeping the mandatory guard in the API handler — rejected: STRUCTURE rule 6, and the seed/migration path is a second writer from day one. Encoding mandatory-ness as a new `KitSourceKind` value — rejected: origin and mandatory-ness are independent axes, and a fourth source kind would leak into the fork and edit-fork rules the 2026-09-16 ADR pins. An `EnsureSingleActiveKit` domain method instead of dropping the constraint — rejected: it would freeze the schema's own many-to-many shape at the object layer and re-break on the first stacked-kit dogfood.
**Consequences:** Multi-kit projects are the normal case, and the "switch kit" UI flow of the superseded ADR is demoted to an optional convenience (kit UI is 250 T4). Two kits whose names slug identically (`Kit One` and `kit-one`) still collide on the bootstrap path, and the second activation is then refused by the overwrite guard naming the path — the collision window shrinks from "any two kits" to "two kits with slug-equal names"; no extra guard is worth its cost. The ceremony kit's bootstrap directory reads `overmind-bootstrap-overmind-ceremony` — redundant by design, a special case for one kit would be the thing that surprises a reviewer. On existing installs the shared `overmind-bootstrap/SKILL.md` stays tracked and watched by drift detection until its kit is next activated, at which point the prune removes file and row together; nothing else rewrites it and nothing needs to. A mandatory kit can no longer be activated per project at all, so between this task and feature 251's home door its content is undeployable by design — the refusal is live while the marking is dormant, because `build/pack.sh` and `build/windows/pack-win.ps1` still emit the legacy string array (`mandatory: false` for every kit); 250 T3 switches the emitters to the object form, and the R2 user-facing copy that explains the global semantics belongs to T4. The prune adds a warning to every activation that still carries an old-layout row, which is the visible signal a stale project is converging.

## Delegated approvals (chat-as-proof) and the embedded session role (007) — 2026-11-02
**Status:** Accepted (spec 007 D2/D3; extends "Two HTTP doors for one aggregate", 2026-09-13 — no override)
**Context:** The embedded management agent (007) needs the full board surface, including the two actions the two-doors ADR deliberately keeps human-only: spec/plan `validate` and the feature `done` flip. The owner wants to instruct the agent in chat ("approve spec of 007") and have the call go through — without the agent ever becoming able to *decide*. The two-doors ADR anticipated agent-scoped policy landing on the agent door; this is that landing.
**Decision:** Three linked mechanisms, all fail-closed. (1) **Embedded session role** — the Host registers its own `AgentSession` with `Role = "embedded"` (vendor `overmind-host`, alias from `agent.alias`), a server-side row the gates read; external coding agents keep the default worker role and can never qualify — for honest clients: the loopback boundary already trusts local processes (STRUCTURE rule 8), so a hostile local process could forge the session header today, and the real fix is the 185 auth line, not this gate. (2) **Per-project `DelegateApprovals` flag, default off** (`ApprovalSettingsApi`, projects settings UI) — delegation is an opt-in per project, never a global posture. (3) **Chat-as-proof closure** — when the flag is on, the agent loop resolves the conversation's latest user message as the owner instruction at turn start and the tool registry dispatches gated calls with `X-Overmind-Delegated-By: <messageId>`; the agent door validates the grant server-side (embedded role on the caller session, caller session == the embedded session, message role == user, message's conversation scoped to the target project) and stamps the provenance line `[delegated by owner via chat] owner message <id> "<excerpt>"` into the artifact/feature log. Any seam failing — flag off, foreign session, non-embedded role, assistant-role message, message from another project, missing header — returns null and the ordinary human-proof requirement stands (409). Human-gated tools are additionally hidden from the model until the gate arms, and refuse with a teaching message when armed without an instruction, so the model is never left guessing at a 409.
**Alternatives considered:** Per-action confirmation UI for every agent mutation — rejected at spec time (confirmation fatigue; the agent already refuses to guess and can ask via `notify_human`). Widening the gate to all agent tools or dropping the human proof when the flag is on — rejected: that would silently override the two-doors ADR; the flag changes WHO executes, never WHETHER a human decided. Trusting the `X-Overmind-Delegated-By` header as sent — rejected: the gate would become a parameter any caller can omit or spoof; the server-side conversation-store validation is what makes the header a closure rather than a claim. Keying delegation on the conversation turn text (semantic "did the owner really approve?") — rejected: unverifiable; the citation is a concrete message id a human can audit.
**Consequences:** The trust model stacks four independent layers: loopback-only binding (a remote caller reaches none of this), the default-off per-project flag, the embedded-role server-side check, and the permanent audit trail — the provenance line carries the cited message id, and the conversation rows persist in SQLite, so every delegated approval is reconstructible after the fact. The known softness is stated plainly: a chat instruction is weaker proof than a UI tap, and the instruction is resolved as *the latest user message* at turn start — any user-role message in the scoped conversation qualifies; the excerpt in the log makes exactly what was "proved" visible, which is the accepted trade-off for the single-owner, loopback MVP. The grimoire memory integration that rides the same embedded session has an honest wire gap, recorded here because it touches the same identity story: Grimoire's HTTP write path accepts no actor field (writes land as Actor=Human Grimoire-side), so agent identity rides provenance tags (`overmind://actor/<alias>`, `overmind://vendor/overmind-host`) on every memory write instead of the actor column — Grimoire-board issue `920d8098` tracks the optional actor passthrough and the missing compaction-candidates endpoint (the self-compaction sweep degrades with typed outcomes until it ships).

## Inno Setup over MSIX/WiX/Velopack for the Windows installer (003b) — 2026-09-21
**Status:** Accepted (spec 003b D1; extends "Portable-first distribution over MSIX/pkg-first", 2026-09-16)
**Context:** 003a shipped the portable archive channel and deferred a real Windows installer to 003b once a Windows build host became available. The MCP adapter's entire delivery model depends on an agent (Claude Code and friends) being able to spawn `overmind-mcp.exe` from a stable, predictable path — that constraint, more than any packaging convenience, decided the technology.
**Decision:** The installer is an Inno Setup script (`build/windows/overmind.iss`) compiled by `ISCC.exe` into one `setup.exe`, built by a self-contained `build/windows/pack-win.ps1` (web build, both publishes, crew-kit staging, ISCC — one command on a Windows machine). Rejected alternatives, in order of consideration: **MSIX** — its payload lands in `C:\Program Files\WindowsApps\<versioned-package-id>\`, a directory with restrictive ACLs whose name changes on every update, so an external agent has no stable path to `overmind-mcp.exe`; sideloading also requires signing, which this unsigned personal tool does not have. **WiX v5** — the transactional install and GPO/Intune deployment story of MSI buys nothing for a personal developer tool and costs Component/GUID ceremony over ~650 published files. **Velopack** — ships an auto-update mechanism, which 003a already rejected as a non-goal, and adds a production dependency for a capability nobody asked for.
**Alternatives considered:** See rejected options above; no fourth candidate was seriously evaluated once the MCP stable-path constraint ruled out MSIX, since that was the strongest architectural argument. Continuing portable-only on Windows was also considered and rejected — a `run.cmd` double-click gives no Start Menu entry, no autostart, no uninstall story, and no PATH integration for `overmind-mcp`, all of which 003b's spec (D2/D3) required.
**Consequences:** Building the Windows installer requires a Windows machine with Inno Setup installed (`winget install --id JRSoftware.InnoSetup`) — the Linux host can no longer produce every distribution artifact alone, extending the "two independent packaging scripts" trade-off already accepted in D4/D12. The installer is unsigned, so every install trips a SmartScreen prompt (documented for users, not worked around per spec R10). `build/dist-layout.env` is the shared layout contract between `pack.sh` and `pack-win.ps1`; `overmind.iss` itself restates the `host`/`mcp`/`web` folder names as literals rather than reading the contract (recorded as a BACKLOG hardening line — self-revealing at compile time for `[Files]`, silent-drift risk for `[Icons]`/`[UninstallDelete]`).

## POST /api/shutdown as the Host's stop contract (003b) — 2026-09-21
**Status:** Accepted (spec 003b D7, R1)
**Context:** The Host is a windowless Avalonia tray process (P/Invoke tray icon, no window handle) with no clean way to stop it from outside: `WM_CLOSE` via `taskkill` has no window to target, Windows Restart Manager is unreliable against a process it cannot enumerate a window for, and `taskkill /F` on a process holding an open SQLite WAL connection is not an upgrade or uninstall strategy — it risks a half-written page and always skips graceful drain. The Windows installer (003b) needs to stop a running Host before it can safely replace files on upgrade or delete them on uninstall.
**Decision:** `POST /api/shutdown` on the human door (`src/Overmind.Host/Api/ShutdownApi.cs`) answers `202 Accepted` — written via `Response.OnCompleted` before shutdown begins, so the caller learns the request was accepted rather than losing the connection — then calls `IHostApplicationLifetime.StopApplication()` to drain in-flight requests and shut down gracefully. The installer's Pascal Script (`overmind.iss`) reads `~/.overmind/host.port`, probes `/api/health` for a live, matching instance, POSTs `/api/shutdown`, and polls up to 10 seconds for the process to clear before falling back to a user-scoped `taskkill /F` as a last resort. The endpoint lives on the human door only; the agent door and the MCP contract are untouched. The MCP adapter (`overmind-mcp.exe`) gets no equivalent graceful path — it is a stdio-only child process with no HTTP surface and no control channel of its own, so `StopRunningMcpAdapter` in `overmind.iss` terminates it unconditionally with a user-scoped `taskkill /F /IM overmind-mcp.exe` at both `PrepareToInstall` (before an upgrade copies over `{app}\mcp`) and `usUninstall` — not a fallback after a timeout, a hard kill by design every time, because there is no softer option to try first.
**Alternatives considered:** A separate helper process/pipe that the installer starts to send a custom stop signal — rejected: the Host already exposes a loopback HTTP API that every other control operation goes through, and a bespoke IPC channel would be a second surface with its own security and versioning story for one call. Relying solely on Windows Restart Manager (`CloseApplications=yes`) — rejected: the Host has no window for RM to track reliably, and RM closing the process abruptly forfeits the graceful-drain guarantee this ADR exists to provide; RM stays off (`CloseApplications=no`) and `PrepareToInstall` does the stopping explicitly. `taskkill /F` as the Host's only mechanism — rejected: no drain, no guarantee the SQLite WAL checkpoint or in-flight writes complete cleanly; kept only as a bounded fallback after the graceful path times out. For the adapter specifically: a loopback control endpoint of its own, mirroring the Host — rejected, it is a thin, disposable stdio process spawned fresh by whatever MCP client owns it, with no persistent state to drain, so adding a server surface for one shutdown call is a bigger control surface than the problem needs. Leaving it running and letting file replacement fail on a locked DLL — rejected, that was CRITICAL-1 in the 003b/03 hard review; an upgrade must not leave a half-replaced `{app}\mcp`.
**Consequences:** Any local process can now stop the Host by hitting a loopback endpoint — the same trust model as the rest of the loopback API (Kestrel binds `127.0.0.1` only; a local user or process is already trusted, per STRUCTURE.md rule 8), but worth writing down explicitly since this endpoint's whole purpose is to terminate the application. The endpoint is exercised three independent ways: a unit test asserting `202` + `ApplicationStopping`, a live run against the real published binary in `smoke-installer.ps1` cell 7, and the installer's own upgrade path in cell 9 (confirmed via the Host's own "Application is shutting down..." log line, not merely a process-exited check, to distinguish a graceful stop from a kill). The adapter's hard-kill consequence is user-visible and unconditional, not merely a fallback: any install or uninstall — not only an upgrade over a locked adapter — terminates every `overmind-mcp.exe` the invoking user owns, including one serving a live agent session in an unrelated repo; the agent's next tool call fails and the client reconnects a fresh adapter process on its own retry/respawn logic, so the failure is recoverable but not silent, and `smoke-installer.ps1` documents and guards this same side effect in its own usage header and preflight cell.

## Backlog importer: legacy status mapping and round-trip closure (008) — 2026-09-17
**Status:** Accepted (spec 008 IMP-1..IMP-5; closes the importer losses declared during the 0.1.0 dogfood)
**Context:** Dogfooding 0.1.0 against this repo's own BACKLOG surfaced four importer gaps. Legacy `status: approved` (historically FROZEN) in 001-era spec/plan imported as `draft`, silently demoting frozen artifacts and poisoning the human-validation lifecycle on re-export. `result.md` was never read, so any repo the materializer had written a result into lost it on re-import — a round-trip hole. Frontmatter values carrying inline annotations (`approved        # draft | approved`) never matched any status. And letter-suffixed task files (`01b-*.md`, used for mid-sprint inserts) failed the strict `NN-` prefix check and were skipped outright. Skipped content was also invisible: the CLI printed only a count.
**Decision:** Frontmatter token parsing strips inline comments (first ` #` to end of line) before lookup (IMP-2). `MapSpecOrPlanStatus` becomes `MapDocumentStatus`: legacy `approved` maps to `validated` for spec/plan documents only, where approved historically meant FROZEN (IMP-3). `result.md` imports as a `result` artifact at order 0, sharing the spec/plan `{draft, validated}` status map — the import → materialize → re-import round-trip with the materializer is closed (IMP-4). Letter-suffixed task filenames are accepted: the base digits give the order, and on a collision the file appends at max+1 ascending by letter, reported loudly as `reassigned:` in the Skipped list (IMP-5). The `--import-backlog` CLI prints every `report.Skipped` entry on its own line after the summary (IMP-1).
**Alternatives considered:** Keep legacy statuses defaulting (the previous behavior) — rejected: silent status loss on every 001-era import, exactly the class of drift the importer exists to prevent. Map `approved` for all artifact kinds — rejected: tasks never carried that status; widening the mapping invents history. Sub-order numbering for letter-suffixed files — rejected: fractional orders do not exist in the domain; refusing them outright was the previous behavior and dropped content silently. Keep skipping `result.md` — rejected: the materializer writes it, so an importer that ignores it cannot round-trip its own repo.
**Consequences:** Frozen lifecycle semantics survive an import of legacy repos; re-importing a materialized repo is loss-free for everything the materializer writes. The `reassigned:` append-at-tail rule trades filename stability for zero data loss — the report entry is the contract that makes the trade visible. `requirements.md` and the `BACKLOG.md` index remain unread, still recorded as declared losses in `CONTEXT.md`.

## Portable-first distribution over MSIX/pkg-first — 2026-09-16
**Status:** Accepted (spec 003 D1, D9; the 003a/003b split)
**Context:** Feature 003 promises "download and run" with pre-bundled kits, but the dev host is Linux: MSIX requires Windows packaging/tooling and a Windows machine to verify, `.pkg` requires macOS — either would block the whole feature on hardware that does not exist yet, and there is no CI. Meanwhile `dotnet publish -r --self-contained` cross-targets win/osx from Linux fine, and the Host already serves the web static export from a configurable root.
**Decision:** 003a ships self-contained portable archives (win-x64, linux-x64, osx-x64, osx-arm64) built by a repo-hosted, shell-only `build/pack.sh` on the Linux host: Host + MCP adapter + web export + `install.sh`/`install.ps1` + the read-only `bundled/` snapshot with `manifest.json`, one archive per RID with SHA-256 sidecars; `dist/` stays gitignored. Install scripts unpack to a user-chosen folder and register OS autostart (XDG / Startup shortcut / launchd plist) and nothing else; upgrade = replace the folder — `bundleVersion` bumps drive the bundled-kit upgrade sync at boot, there is no app auto-update. Uninstall = delete the folder (`~/.overmind` untouched). MSIX/pkg proper installers, code signing and store distribution move to 003b, blocked on a Windows/macOS build host or CI runners. Verified posture: linux smoke-tested end to end (`build/smoke.sh`); win/osx archives are build-verified only (cross-publish + sidecar + forbidden-path scans, no run).
**Alternatives considered:** MSIX/pkg-first — rejected: blocked on native hosts, would delay shipping the bundled-kits value indefinitely for packaging's sake. Linux distro packages (deb/rpm/flatpak) — rejected as a non-goal: a tar.gz + install script is not a package, and per-distro maintenance is a separate commitment. CI-based cross-build — rejected for 003a: no CI exists (D9); the shell script is the CI input later.
**Consequences:** Distribution ships now on all four RIDs from one Linux command. The archive layout (`host/bundled/` next to the binary, run launchers pinning `OVERMIND_WEB_ROOT`) becomes a contract the boot seed and install scripts consume. `install.ps1` and the macOS plist registration are best-effort and unverified at runtime — 003b may need a fix-forward. No code signing and no auto-update: users re-download archives and trust the sidecar hashes.

## Bundled kits are a source kind with edit-fork semantics, not a separate pipeline — 2026-09-16
**Status:** Accepted (spec 003 D2–D7; closes NIT-3 from the 002/02 hard review)
**Context:** The distribution ships curated kits that must take updates on upgrade yet never clobber user personalization, riding the 002a import pipeline (scan/commit/diff already exist). The open 002/02 review nit asked what `ClearSource()` should do once a `Bundled` kind exists. The load-bearing question is where "bundled" lives: a parallel import path would fork the pipeline, and copy-on-edit would duplicate kits in the library.
**Decision:** Bundled is an origin flavor, not a pipeline branch: `KitImporter` commit and re-import take a `bundled` flag — same transaction, same entries/hashes/diff, origin stamped via `SkillKit.MarkBundled(sourcePath)` (`ImportedAtUtc` stays null; a bundled refresh re-stamps the same way, so origin survives the three-way diff). Personalization converts in place: the first content edit of an entry owned exclusively by a bundled kit calls `SkillKit.ForkToManual()` — the kit becomes an ordinary `manual` kit in the same transaction as the entry update (no copy-on-edit; entries shared with another kit mutate directly and never fork; title/tag/skillfile-only updates never fork). Upgrade sync then skips it by construction, because it is no longer `Bundled`. The exits are deliberate: `ClearSource()` refuses a bundled kit with typed 409 `BundledSourceProtected` (NIT-3 closed — the exit is edit-fork or delete), and an external `POST /api/kits/{id}/reimport` on a bundled kit returns typed 409 `BundledReimportBlocked` — refresh is upgrade-sync's job, keyed to `bundleVersion`, not a user action.
**Alternatives considered:** Copy-on-edit (fork creates a duplicate manual kit, bundle stays) — rejected: doubles library entries on every first edit, breaks the simple "badge flips" story, and the user edits *their* kit, not a derived clone. Bundled kits immutable (edits refused) — rejected: kills personalization, the point of kits. Allow clear-source/re-import on bundled like imported — rejected: a cleared bundle would strand a kit that looks manual while its upstream keeps shipping, and a manual re-import would race the bundleVersion-keyed upgrade semantics. A separate bundled import path — rejected: second writer for the same aggregate, exactly the duplication the planning-services ADR warns about.
**Consequences:** One import pipeline, three origin flavors; 002b (`.omkit`) inherits the same extension point. The silent origin flip on first edit is a UX hazard mitigated by the web hint ("Edits fork this kit into your personal copy.") and the badge flip, not a modal. Shared-entry edits never fork — an edited shared entry stays in the bundled kit, documented as the 003a exclusion. `ForkToManual` is deliberately unconditional (the call site gates on `SourceKind == Bundled`); `ClearSource` stays the refusing guard next to it.

## Bundled boot seed and upgrade sync are swallow-and-log behind a stamped once-flag — 2026-09-16
**Status:** Accepted (spec 003 D3, D4; mirrors the planning materializer sync posture)
**Context:** Bundles are a boot-time concern: the Host must start even when the bundle is missing, corrupt, partially failing, or relocated, and seeding must happen exactly once per version without resurrecting kits the user deleted. The planning materializer already established the posture for "disk follows DB, never blocks the primary path" — the inverse question here is "bundle follows distribution, never blocks startup."
**Decision:** `BundledSeedService` runs in the Host boot scope right after `MigrateAsync`, before the API accepts requests, and never propagates failures: missing bundle, invalid manifest (`BundledManifest.TryLoad` returns false, no throw), and per-kit import errors are caught and logged (structured Serilog; `OperationCanceledException` rethrows, mirroring `BacklogImportCommand`). The once-guard is the stamped `AppSetting` flag `BundledSeedVersion`, not library emptiness: seed fires only on an empty library with no flag; a non-empty flagless library is `LibraryInUse` and stamps nothing, so a library that later empties still seeds, while a user who deletes all kits after seeding gets nothing back. Upgrade sync (stored version < manifest `bundleVersion`) adds missing kits, refreshes bundled kits through the three-way diff (repointing a stale `SourcePath` first so a relocated install does not stick on `SourceMissing`), skips manual/imported name collisions, and stamps the new version even when some kits fail — recovery is the next bundle bump, not a boot retry-loop.
**Alternatives considered:** Fail startup on seed/sync failure — rejected: a corrupt bundle would brick the app for a feature that is a convenience; same reasoning as the planning sync ADR. Stamp only on full success — rejected: one bad kit would re-run the whole pass on every boot (write churn, log spam, repeated partial imports). Guard on library emptiness alone — rejected: deleting all kits would resurrect bundles the user deliberately removed. Retry scheduling at runtime — rejected: boot-time only keeps a single-writer window before the API accepts requests; no background loops in v1.
**Consequences:** Bundles are best-effort at boot: a partially seeded bundle needs a `bundleVersion` bump (or manual re-import) to retry — accepted, recorded in the plan's risks. The `LibraryInUse` nuance means an imported-from-folder-then-emptied library seeds bundles later (fresh-machine semantics, intended). Seeding runs in the pre-API startup window, so there is no user-visible race with imports; concurrent first-boot writes are impossible by construction (single instance lock + sequential boot).

## Kit import is a snapshot into the DB, not file-backed kits — 2026-09-16
**Status:** Accepted (spec 002 D1)
**Context:** Feature 002 makes kits importable from local folders; the load-bearing question is what the folder becomes afterwards. The DB already owns FTS indexing, `EntryVersion` history, the materializer and drift detection; a second, file-backed kit posture would need parallel versions of all four or would degrade imported kits to second-class citizens.
**Decision:** Import parses the folder once and creates ordinary `ContextEntry` rows — skills with per-platform `SkillFile`s, gates, guards — linked to a `SkillKit` carrying its origin (`SourceKind: imported`, `SourcePath`, `ImportedAtUtc`). FTS, `EntryVersion`, materializer and drift work unchanged on imported entries. The source folder is not needed after import; there are no file-backed kits. Re-import (an explicit user action) re-reads the folder and applies the three-way diff ADR; "clear source" converts the kit to `manual` and detaches it from the path.
**Alternatives considered:** File-backed kits with live sync (watcher) — rejected: duplicates versioning/search/materialization machinery for a second storage posture, adds watcher and removable-path complexity; the "living source" need is the future v2 git-linked-kits feature (removed from 002 scope 2026-09-14). Import as opaque archive blobs — rejected: content invisible to search, versions and materialization.
**Consequences:** No live synchronization — edits to the source folder appear only after a manual re-import, and a missing/moved source path is a typed 409, not data loss (the DB snapshot stands alone). Imported and hand-made kits are indistinguishable downstream, which is what lets 002b (`.omkit` export/import) and 003 (bundled kits) ride the same pipeline unchanged.

## Cross-platform skills: agnostic-by-default with byte-identical pass-through — 2026-09-16
**Status:** Accepted (spec 002 D3, R11; records the 002/01 spike verdict)
**Context:** A scanned folder may mark platform-specific skills by placing them under a platform directory; everything else must work for every supported agent. Materializing one agnostic SKILL.md to six platforms is only safe if no per-platform frontmatter transform is required — spec R11 demanded the spike before any materializer change (five platforms researched from official docs plus local inspection; matrix and sources in `BACKLOG/002-kit-library/tasks/01-format-spike.md`).
**Decision:** Platform directories come from `platforms.json` (the same map the materializer reads); a skill under `<platform-dir>/skills/<skill>/` imports as a per-platform variant, any other skill as platform-agnostic — a single `SkillFile` with a null platform. At materialization, a null-platform `SkillFile` expands to every known platform directory. Frontmatter passes through byte-identical: the spike verdict is pass-through — observed deltas are additive optional fields that off-platform loaders ignore and narrower validation on some platforms, which are authoring-time constraints (the spike's import gates G1–G5), not materialization transforms. `qwen` was added to `platforms.json` and the `AgentPlatform` enum during the spike. Codex `.codex/skills` was verified against the official docs and is NOT a documented Codex skills path — recorded as a deferred P1 item (moving codex to `.agents/skills` needs a design decision; that alias is also read by Kimi/Gemini).
**Alternatives considered:** Per-target normalization at materialization — rejected on spike evidence: no delta requires a transform, so it would be speculative code against six targets. Normalize once at import — rejected: bakes platform assumptions into the snapshot, diverges from the source bytes, and still needs the spike to prove which transforms.
**Consequences:** Adding a platform is a `platforms.json` entry (no recompile) and agnostic skills expand to it automatically. Byte-portability constraints live at authoring time — a body referencing platform-specific skill-dir env vars (`${CLAUDE_SKILL_DIR}` vs `${KIMI_SKILL_DIR}` vs `$QWEN_SKILL_ROOT`) is not byte-portable, recorded in the spike for kit authors. ## Re-import is a three-way diff on per-entry import hashes; skills are keyed by kit-root relative path — 2026-09-16
**Status:** Accepted (spec 002 D8, R8–R10; includes the 002/09 e2e closeout fix)
**Context:** Imported kits must track an evolving source folder without clobbering local edits: for each entry, "user edited here" and "file changed there" can both be true and neither may silently win. Matching entries to files also needs a stable identity — the first implementation reconstructed a key from `{skillsDir}/{title}`, which diverged from the scanner's kit-root-relative paths for subfoldered skills: the closeout e2e showed agnostic skills under `skills/` falling out of matching entirely (removed + re-added, losing the local edit and version history) — a BLOCKER found and fixed in the same change.
**Decision:** `SkillKitEntry` carries `ImportedContentHash` (SHA-256 of normalized content at last import, same normalization as materialization hashes) and `RelativePath` (the skill's path from kit root; the candidate prefix is stripped at commit). Per entry: file unchanged since import → keep local edits; entry unchanged since import → take the file content as a new `EntryVersion`; both changed → conflict: the entry is refused, local content and the old hash are kept so the next re-import still sees the conflict; new files → new entries; files gone → the kit-owned entry is removed. Pre-`RelativePath` rows fall back to the old `{skillsDir}/{title}` / `{title}` reconstruction (nullable column, migration `20260916083250_SkillKitEntryRelativePath`). Gates and guards are matched by title (`DiffRuleFilesAsync`) — their titles come from the Overmind-owned H1/filename convention and are stable; path-based identity for rule files is the deferred 002/06 hardening item, not current behavior.
**Alternatives considered:** Last-writer-wins on either side — rejected: silent data loss in the exact case the feature exists for. Content merge of the two sides — rejected: markdown merging is unreliable and v1 has no merge UI. Matching by title alone — rejected: renames and duplicate titles break identity, and the reconstructed key already demonstrated the failure mode.
**Consequences:** Outcomes are per-entry granular (added / updated / kept-local / conflicted / removed) and the report distinguishes removed-and-deleted from removed-link-retained when another kit still shares the entry. For skills, path is the identity — a rename on disk reads as remove + add — accepted. The e2e scenario is pinned by `KitReimportTests` (subfolder matrix, prefix canonicalization, two-platform variants, null fallback).

## Kit import API: read-only scan, per-kit transactional commit — 2026-09-16
**Status:** Accepted (spec 002 D10, D9; recorded at 002a closeout)
**Context:** A scanned folder may contain several kit candidates with editable names, per-file issues and name collisions — the user must see and shape what will happen before anything is written. At commit time a partial failure (one bad kit in a multi-kit folder) must not poison the rest, and two callers picking the same kit name concurrently must not both succeed.
**Decision:** Two phases. `POST /api/kits/import/scan` is read-only and side-effect-free: it returns candidates (the folder itself plus each qualifying top-level subdirectory), their entries with detected platforms/types, per-file issues, name-collision flags and existing-kit matches by `SourcePath` (re-import pointers). `POST /api/kits/import` commits with one transaction per selected kit and returns per-kit reports — a failing kit rolls back fully and is reported while the others import. `POST /api/kits/{id}/reimport` and `POST /api/kits/{id}/clear-source` are kit-scoped. Import selections match candidates by `relativePath` (root candidate `""`), never by name. The synthetic "Kit Library" project is protected by a delete guard: `ProjectsApi.Delete` returns 409 while the project owns kit-linked entries. `SkillKits.Name` carries a unique index (BINARY collation, migration `20260915120341_UniqueKitName` with migration-time dedup renaming duplicates to `Name (2)`, `Name (3)`, … by rowid); violations map to a per-kit `DuplicateName` failure in the importer and 409 in `KitsApi` create/update.
**Alternatives considered:** Single-phase import (write on scan) — rejected: no preview for multi-kit folders, renames and deselection impossible. One transaction across all kits — rejected: a single bad kit fails the whole folder, exactly the blast radius per-kit atomicity exists to avoid. Match selections by candidate name — rejected: ambiguous when the folder root's basename equals a top-level subdirectory name (the root candidate silently won a `FirstOrDefault` — found in the 002/08 review and fixed by the relativePath contract).
**Consequences:** Scan can be invoked freely with nothing to clean up. Kit name uniqueness is enforced twice (in-memory OrdinalIgnoreCase check stays the primary guard; the index closes the exact-name commit race). `KitImportException`/`KitImportFailureKind` is the single error vocabulary; request-level failures become ProblemDetails via `KitImportErrors`, while per-kit commit failures ride the report — one import request can mix successes and failures in one 200.

> **Amended 2026-11-19 (feature 250, T3 widening → T8) — a candidate may qualify on root prose.** A top-level subdirectory now becomes a candidate even with no skill, gate or guard inside, when it keeps at least one `.md` file of its own at that folder's root (other than `SKILL.md`; `gates` and `guards` never qualify this way). The six-kit bundle ships a prose-only kit — `sociality` is a single `SOCIAL_DICTIONARY.md` — and under the accepted rule its scan produced no candidate, so a fresh install failed one of six imports. Two side effects are accepted with it: a folder shaped like a platform directory (`.claude/`) now lists an empty `agents` candidate, so the name `agents` can reach the unique-name index; and a prose-only kit imports with zero entries, because the importer maps skills, gates and guards only — its content reaches users through feature 251's home-deploy door or the copy-as-delivery route, while per-project activation materializes nothing from it. The `.md` gate is the T8 correction of the T3 review finding that the widening accepted any file at a folder root, which made `build/` (shell scripts) a candidate when scanning an arbitrary repository root; both directions are pinned by `KitScannerTests.Scan_FolderRoots_QualifyMarkdownProseButNotScripts`.

## Two HTTP doors for one aggregate: `/api/planning/*` and `/api/agent/planning/*` — 2026-09-13
**Status:** Accepted
**Context:** Spec 006 (R3) requires the validation gate to distinguish an agent from a human: when human validation is effective, only the UI may approve a spec/plan. At the same time R2 demands one service path for the HTTP API and MCP — status enums and frozen semantics enforced once, not per surface. So the same planning aggregate needs two caller classes over identical behavior.
**Decision:** One handler set, two route prefixes. The human door is `/api/projects/{id}/planning/*` + `/api/planning/*` (`PlanningFeaturesApi`, `PlanningArtifactsApi`, `PlanningWorkflowApi`, `PlanningMaterializationApi`); the agent door is `/api/agent/planning/*` (`AgentPlanningApi`), which maps onto the same `internal static` handler delegates and adds only what is agent-specific: `current` (stop/empty/task states) and the gated `validate`, which resolves the gate first and returns 409 `HumanValidationRequired` with a `STOP:` detail when effective. Caller identity is carried by the route prefix — never by a request parameter.
**Alternatives considered:** An actor flag in the body or query (`?actor=agent`) — rejected: the gate becomes a parameter any caller can omit, and the MCP adapter would have to be trusted to send it truthfully. An `X-Overmind-Actor` header — rejected for the same reason with a thinner audit trail. Two separate handler sets — rejected: duplicates R2's single enforcement path and invites drift between doors.
**Consequences:** The agent door is the natural place to add agent-scoped policy later (rate limits, write scopes, agent identity). New planning routes must be mapped on both doors deliberately — forgetting the agent mapping narrows the agent surface with no compile error; the MCP planning tools and the web UI are the two consumers that would notice.

## MCP adapter bypasses the system proxy on loopback — 2026-09-12
**Status:** Accepted
**Context:** A bare `new HttpClient()` honours the system proxy (`SocketsHttpHandler` default `UseProxy = true`). Measured on the dev machine (`audits/audit-2026-09-10.md`, BLOCKER-1): with a system proxy on `127.0.0.1:2080` and no bypass list, every MCP-adapter call to the Host at `127.0.0.1:4761` was routed through a third-party proxy process — breaking the "loopback is the security boundary" rule, producing `502 Bad Gateway` instead of "unreachable" when the Host is down, and making the Mcp contract suite environment-dependent (green with the proxy off, red with it on). Recorded 2026-09-12; the fix shipped 2026-09-10 (commit `7394389`).
**Decision:** `OvermindApiClient.CreateHttpClient` builds `new SocketsHttpHandler { UseProxy = false }` (`src/Overmind.Mcp/OvermindApiClient.cs:57`), with a comment in code stating why so it does not get "cleaned up". Scope is `Overmind.Mcp` only: Infrastructure embedding providers keep proxy support, because their base URLs (Ollama, OpenAI-compatible) may be remote.
**Alternatives considered:** Rely on the OS proxy bypass list (`ProxyOverride` / `no_proxy`) — rejected: it is machine configuration we neither own nor can verify at runtime. Bypass the proxy process-wide — rejected: embedding providers legitimately need the proxy for remote URLs.
**Consequences:** Loopback Host traffic never leaves the loopback regardless of system proxy state; the Mcp test suite is proxy-independent. The SPA side is not covered — browsers may still proxy `*.localhost` (see ADR "Browser URL is `overmind.localhost`" and the P0 check in `BACKLOG.md`).

## Browser URL is `overmind.localhost` — 2026-09-12
**Status:** Accepted
**Context:** The Host opens the SPA in the default browser at startup and on single-instance relaunch. Opening `http://127.0.0.1:<port>` works but is opaque in the tab bar/history and shares the browser's `127.0.0.1` origin jar (cookies, storage) with anything else bound there. `*.localhost` names resolve to loopback per RFC 6761 and via systemd-resolved/nss-myhostname on Ubuntu. Shipped as `BrowserUri.FromLoopback` (commit `66f51b8`); recorded here 2026-09-12 after the audit flagged it as untracked work.
**Decision:** `BrowserUri.FromLoopback` (`src/Overmind.Host/BrowserUri.cs`) rewrites the bound URL's host to `overmind.localhost` when it is `127.0.0.1`/`localhost`/`[::1]`, and leaves any non-loopback bind untouched. The rewrite is browser-facing only — Kestrel still binds `127.0.0.1`.
**Alternatives considered:** Open `127.0.0.1` directly — rejected: poorer UX and shared origin jar. Register a real local hostname / mDNS — rejected: platform-specific setup for a cosmetic gain.
**Consequences:** Works out of the box on Ubuntu (systemd-resolved) and Windows/macOS. Known caveats, accepted: minimal systems without nss-myhostname may not resolve `*.localhost` (fallback: browse to `http://127.0.0.1:<port>` from the port file); browsers behind a system proxy may proxy even `*.localhost` — tracked as the P0 manual check in `BACKLOG.md`.

**Status:** Accepted (spec 049; supersedes the `BACKLOG.md`-index references in the consequences of "Backlog importer: legacy status mapping and round-trip closure" (008), "Planning conventions: canonical version numbering and enum posture" (006), "MCP adapter bypasses the system proxy on loopback" and "Browser URL is `overmind.localhost`" — those lines stay as written per ADR immutability, this ADR is the correction)
**Context:** The managed `BACKLOG.md` block predates the MCP planning surface: a generated index was the only way for a file-only reader to see statuses, execution order and deferred hardening. By 049 the index had no audience left — agents read the board through `planning_list_features`/`planning_task_queue`, the UI renders the same board, and the materialized `BACKLOG/` tree already carries per-feature state in `feature.md`. The second copy kept costing real drift: every index row was one more place a status could go stale, block-only hashing special-cased the drift/delete paths, and tests pinned a generated file nobody read.
**Decision:** Remove the writer, not the file: `PlanningMaterializer` no longer builds a `BACKLOG.md` plan entry, and the managed-block render/merge path is gone — no fresh index row is ever created. The board is the only live state copy; the `BACKLOG/` tree remains the disk contract (read-only materialized feature folders + ENTRIES/). Legacy rows written by pre-049 builds migrate through the existing stale-row machinery instead of a dedicated migration: the next pass strips the managed block (block-only hash; hand-written content outside the markers survives byte-for-byte), deletes the row and never touches the file again — a hand-edited block refuses the pass (033 semantics), `force` strips with a per-file warning. The hand content left in the retired file is preserved by replacing the file with a static git-tracked pointer (a `<removed ...>` tombstone header plus the mirror bullets) — a deliberate human-editable commit, not a materializer write.
**Alternatives considered:** Keep generating the index (status quo) — rejected: a second state copy whose only consumers were superseded by the MCP board tools and the UI board; the drift cost was pure tax. Delete `BACKLOG.md` outright during migration — rejected: a silent removal of a tracked file plus loss of hand-written Deferred content, where the stale-row machine gives a guarded strip instead. Teach the importer to read the index back — rejected: reading a generated copy as input legitimizes exactly the second copy this decision removes.
**Consequences:** Fresh projects never get `BACKLOG.md`; this repo's own file becomes a static pointer, and any status read from it is stale by definition — check the board. `ManagedBlock` keeps only the legacy strip path (markers, `TryExtract`, `Remove`), so block-only hashing lives on solely for pre-049 rows and shrinks with every migrated project. Docs no longer name the index as work tracking; hardening nits that used to collect in the file's Deferred section land on the board (the microbatch queue entry).

## The mirror is untracked by default; export is the commit-alongside path (075) — 2026-10-13
**Status:** Accepted (spec 075 D1–D3; extends "Planning materialization defaults to on", 2026-09-23)
**Context:** The 2026-09-23 ADR made materialization default-on, so every fresh project grows a `BACKLOG/` tree (and since 051 an `ENTRIES/` projection) inside what is usually a git working tree. Ceremony traffic made the cost visible: 77-entry sessions produce constant mirror churn, and `git status` noise grows octal ladders — `\320\276\320\261…`-style quoted paths from Cyrillic feature titles — burying every real change. The standing posture — the mirror is just working-tree content, commits belong to whoever works the branch — left each repo to gitignore the mirror by hand or commit a generated tree nobody meant to own, and Overmind had no way to hand a board snapshot to a repo that does want the planning committed alongside the code.
**Decision:** Three moves. (1) Untracked by default, mechanically rather than by advice: every materializer pass runs `MirrorGitHygiene` — walk up from the materialization write root to the nearest `.git/` directory and idempotently ensure the repo-root-relative `BACKLOG/` + `ENTRIES/` patterns in `.git/info/exclude`, git's local-only, never-committed ignore file — exactly the right scope for a per-install generated tree. The Host never executes git; this is file manipulation only, serialized by a static gate, never failing the pass — the outcome (`ensured`/`already-present`/`no-repo`/`failed`) reports as an additive `GitHygiene` field on `PlanningMaterializationReport`. Exclude does not untrack, so already-committed mirrors are untouched; untracking an existing repo stays the explicit human step (`git rm -r --cached BACKLOG ENTRIES`). (2) The explicit commit-alongside path is the export door: `POST /api/projects/{id}/planning/export` on both doors and MCP `planning_export_backlog` render the full current mirror through the same document renderers the pass uses (extracted `MirrorPlanRenderer` — no second rendering implementation, byte-identical output) into a caller-supplied absolute, empty target directory; zero tracking rows, zero drift machinery — a snapshot, not a sync. Typed refusals: `ExportTargetNotAbsolute` (400), `ExportTargetNotEmpty` (409, an existing file included), `ExportTargetInsideMirror` (409, a target inside `BACKLOG/`/`ENTRIES/` or at the project root), `PathTraversal` (400, a path-guard escape). Export assumes the loopback-only binding; if `Overmind:BindUrl` is ever widened this is the first candidate for `RequireAuthorization`. (3) Mirror filenames are ASCII-safe: slug generation transliterates Cyrillic first (`CyrillicTransliteration`, GOST 7.79-2000 System B family) and strips remaining non-ASCII; the pin is content-hash-gated — a tracked filename whose stored hash equals the freshly rendered document keeps its path — so existing names stay byte-stable while their titles are unchanged, and a title change is what converges the filename.
**Alternatives considered:** Writing the repo's own `.gitignore` — rejected: the Host would have to edit a user-owned, often-committed file (merge conflicts, review noise, exactly the class of hand-edit collisions that make the materializer refuse guarded files), while `.git/info/exclude` is local by design and never leaves the machine. Doing nothing and documenting "gitignore the mirror yourself" — rejected: repeats the 2026-09-23 failure mode the default-on ADR fixed, a posture only agents who read the docs ever hit. Zip archive export — rejected: the point is greppable plain files a repo can commit and diff; an archive is a black box to both git and agents. Forced rename of existing non-ASCII mirror files — rejected: mass renames churn history and break open work for a cosmetic win; the content-hash pin plus natural convergence on title change reaches the same end state without touching a single tracked path. `RequireAuthorization` on the export endpoint now — rejected as premature under the loopback-only bind (STRUCTURE rule 8), recorded above as the first candidate if the bind ever widens.
**Consequences:** Fresh repos get a silent, self-healing exclude and a clean `git status` out of the box; existing tracked mirrors keep working unchanged until the human untracks them. The hygiene outcome is visible on the human-door materialize response only — the MCP tool's compact echo drops it (ledger #324). Export writes outside the project root by design (that is its purpose), guarded by the path guard and the typed refusals; it creates no tracking rows, so exporting into a fresh target is always safe and re-exporting over an existing target is always a 409. Transliteration changes slug output for new and renamed Cyrillic titles; the shared `Slug` primitive also feeds archive root names and skill directory slugs, which pick up the same ASCII behavior (real-world exposure near zero — names are ASCII in practice). The onboard quickstart and the crew-kit ceremony-skill capability matrix carry the hygiene line, so agents meet the export path at onboarding (standing rule 116 — synced in the same wave).
