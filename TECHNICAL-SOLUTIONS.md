# Technical Solutions

Architecture Decision Records. Newest first. Once Accepted, changing a decision requires a new ADR that supersedes the old one — never a silent edit.

## Kit import is a snapshot into the DB, not file-backed kits — 2026-09-16
**Status:** Accepted (spec 002 D1)
**Context:** Feature 002 makes kits importable from local folders; the load-bearing question is what the folder becomes afterwards. The DB already owns FTS indexing, `EntryVersion` history, the materializer and drift detection; a second, file-backed kit posture would need parallel versions of all four or would degrade imported kits to second-class citizens.
**Decision:** Import parses the folder once and creates ordinary `ContextEntry` rows — skills with per-platform `SkillFile`s, gates, guards — linked to a `SkillKit` carrying its origin (`SourceKind: imported`, `SourcePath`, `ImportedAtUtc`). FTS, `EntryVersion`, materializer and drift work unchanged on imported entries. The source folder is not needed after import; there are no file-backed kits. Re-import (an explicit user action) re-reads the folder and applies the three-way diff ADR; "clear source" converts the kit to `manual` and detaches it from the path.
**Alternatives considered:** File-backed kits with live sync (watcher) — rejected: duplicates versioning/search/materialization machinery for a second storage posture, adds watcher and removable-path complexity; the "living source" need is the future v2 git-linked-kits feature (removed from 002 scope 2026-09-14). Import as opaque archive blobs — rejected: content invisible to search, versions and materialization.
**Consequences:** No live synchronization — edits to the source folder appear only after a manual re-import, and a missing/moved source path is a typed 409, not data loss (the DB snapshot stands alone). Imported and hand-made kits are indistinguishable downstream, which is what lets 002b (`.omkit` export/import) and 003 (bundled kits) ride the same pipeline unchanged.

## Cross-platform skills: agnostic-by-default with byte-identical pass-through — 2026-09-16
**Status:** Accepted (spec 002 D3, R11; records the 002/01 spike verdict)
**Context:** A scanned folder may mark platform-specific skills by placing them under a platform directory; everything else must work for every supported agent. Materializing one agnostic SKILL.md to six platforms is only safe if no per-platform frontmatter transform is required — spec R11 demanded the spike before any materializer change (five platforms researched from official docs plus local inspection; matrix and sources in `BACKLOG/002-kit-library/tasks/01-format-spike.md`).
**Decision:** Platform directories come from `platforms.json` (the same map the materializer reads); a skill under `<platform-dir>/skills/<skill>/` imports as a per-platform variant, any other skill as platform-agnostic — a single `SkillFile` with a null platform. At materialization, a null-platform `SkillFile` expands to every known platform directory. Frontmatter passes through byte-identical: the spike verdict is pass-through — observed deltas are additive optional fields that off-platform loaders ignore and narrower validation on some platforms, which are authoring-time constraints (the spike's import gates G1–G5), not materialization transforms. `qwen` was added to `platforms.json` and the `AgentPlatform` enum during the spike. Codex `.codex/skills` was verified against the official docs and is NOT a documented Codex skills path — recorded as a deferred P1 item (moving codex to `.agents/skills` needs a design decision; that alias is also read by Kimi/Gemini).
**Alternatives considered:** Per-target normalization at materialization — rejected on spike evidence: no delta requires a transform, so it would be speculative code against six targets. Normalize once at import — rejected: bakes platform assumptions into the snapshot, diverges from the source bytes, and still needs the spike to prove which transforms.
**Consequences:** Adding a platform is a `platforms.json` entry (no recompile) and agnostic skills expand to it automatically. Byte-portability constraints live at authoring time — a body referencing platform-specific skill-dir env vars (`${CLAUDE_SKILL_DIR}` vs `${KIMI_SKILL_DIR}` vs `$QWEN_SKILL_ROOT`) is not byte-portable, recorded in the spike for kit authors. The codex mapping stays as-is pending the deferred item, so skills materialized there may be invisible to current Codex CLIs.

## Re-import is a three-way diff on per-entry import hashes; skills are keyed by kit-root relative path — 2026-09-16
**Status:** Accepted (spec 002 D8, R8–R10; includes the 002/09 e2e closeout fix)
**Context:** Imported kits must track an evolving source folder without clobbering local edits: for each entry, "user edited here" and "file changed there" can both be true and neither may silently win. Matching entries to files also needs a stable identity — the first implementation reconstructed a key from `{skillsDir}/{title}`, which diverged from the scanner's kit-root-relative paths for subfoldered skills: the closeout e2e showed agnostic skills under `skills/` falling out of matching entirely (removed + re-added, losing the local edit and version history) — a BLOCKER found and fixed in the same change.
**Decision:** `SkillKitEntry` carries `ImportedContentHash` (SHA-256 of normalized content at last import, same normalization as materialization hashes) and `RelativePath` (the skill's path from kit root; the candidate prefix is stripped at commit). Per entry: file unchanged since import → keep local edits; entry unchanged since import → take the file content as a new `EntryVersion`; both changed → conflict: the entry is refused, local content and the old hash are kept so the next re-import still sees the conflict; new files → new entries; files gone → the kit-owned entry is removed. Pre-`RelativePath` rows fall back to the old `{skillsDir}/{title}` / `{title}` reconstruction (nullable column, migration `20260916083250_SkillKitEntryRelativePath`). Gates and guards are matched by title (`DiffRuleFilesAsync`) — their titles come from the Overmind-owned H1/filename convention and are stable; path-based identity for rule files is the deferred 002/06 hardening item, not current behavior.
**Alternatives considered:** Last-writer-wins on either side — rejected: silent data loss in the exact case the feature exists for. Content merge of the two sides — rejected: markdown merging is unreliable and v1 has no merge UI. Matching by title alone — rejected: renames and duplicate titles break identity, and the reconstructed key already demonstrated the failure mode.
**Consequences:** Outcomes are per-entry granular (added / updated / kept-local / conflicted / removed) and the report distinguishes removed-and-deleted from removed-link-retained when another kit still shares the entry. For skills, path is the identity — a rename on disk reads as remove + add — accepted. The e2e scenario is pinned by `KitReimportTests` (subfolder matrix, prefix canonicalization, two-platform variants, null fallback).

## Kit import API: read-only scan, per-kit transactional commit — 2026-09-16
**Status:** Accepted (spec 002 D10, D9; recorded at 002a closeout)
**Context:** A scanned folder may contain several kit candidates with editable names, per-file issues and name collisions — the user must see and shape what will happen before anything is written. At commit time a partial failure (one bad kit in a multi-kit folder) must not poison the rest, and two callers picking the same kit name concurrently must not both succeed.
**Decision:** Two phases. `POST /api/kits/import/scan` is read-only and side-effect-free: it returns candidates (the folder itself plus each qualifying top-level subdirectory), their entries with detected platforms/types, per-file issues, name-collision flags and existing-kit matches by `SourcePath` (re-import pointers). `POST /api/kits/import` commits with one transaction per selected kit and returns per-kit reports — a failing kit rolls back fully and is reported while the others import. `POST /api/kits/{id}/reimport` and `POST /api/kits/{id}/clear-source` are kit-scoped. Import selections match candidates by `relativePath` (root candidate `""`), never by name. The synthetic "Kit Library" project is protected by a delete guard: `ProjectsApi.Delete` returns 409 while the project owns kit-linked entries. `SkillKits.Name` carries a unique index (BINARY collation, migration `20260915120341_UniqueKitName` with migration-time dedup renaming duplicates to `Name (2)`, `Name (3)`, … by rowid); violations map to a per-kit `DuplicateName` failure in the importer and 409 in `KitsApi` create/update.
**Alternatives considered:** Single-phase import (write on scan) — rejected: no preview for multi-kit folders, renames and deselection impossible. One transaction across all kits — rejected: a single bad kit fails the whole folder, exactly the blast radius per-kit atomicity exists to avoid. Match selections by candidate name — rejected: ambiguous when the folder root's basename equals a top-level subdirectory name (the root candidate silently won a `FirstOrDefault` — found in the 002/08 review and fixed by the relativePath contract).
**Consequences:** Scan can be invoked freely with nothing to clean up. Kit name uniqueness is enforced twice (in-memory OrdinalIgnoreCase check stays the primary guard; the index closes the exact-name commit race). `KitImportException`/`KitImportFailureKind` is the single error vocabulary; request-level failures become ProblemDetails via `KitImportErrors`, while per-kit commit failures ride the report — one import request can mix successes and failures in one 200.

## Two HTTP doors for one aggregate: `/api/planning/*` and `/api/agent/planning/*` — 2026-09-13
**Status:** Accepted
**Context:** Spec 006 (R3) requires the validation gate to distinguish an agent from a human: when human validation is effective, only the UI may approve a spec/plan. At the same time R2 demands one service path for the HTTP API and MCP — status enums and frozen semantics enforced once, not per surface. So the same planning aggregate needs two caller classes over identical behavior.
**Decision:** One handler set, two route prefixes. The human door is `/api/projects/{id}/planning/*` + `/api/planning/*` (`PlanningFeaturesApi`, `PlanningArtifactsApi`, `PlanningWorkflowApi`, `PlanningMaterializationApi`); the agent door is `/api/agent/planning/*` (`AgentPlanningApi`), which maps onto the same `internal static` handler delegates and adds only what is agent-specific: `current` (stop/empty/task states) and the gated `validate`, which resolves the gate first and returns 409 `HumanValidationRequired` with a `STOP:` detail when effective. Caller identity is carried by the route prefix — never by a request parameter.
**Alternatives considered:** An actor flag in the body or query (`?actor=agent`) — rejected: the gate becomes a parameter any caller can omit, and the MCP adapter would have to be trusted to send it truthfully. An `X-Overmind-Actor` header — rejected for the same reason with a thinner audit trail. Two separate handler sets — rejected: duplicates R2's single enforcement path and invites drift between doors.
**Consequences:** The agent door is the natural place to add agent-scoped policy later (rate limits, write scopes, agent identity). New planning routes must be mapped on both doors deliberately — forgetting the agent mapping narrows the agent surface with no compile error; the MCP planning tools and the web UI are the two consumers that would notice.

## Planning ceremony mutations live in `Infrastructure/Planning` services — 2026-09-13
**Status:** Accepted (supersedes the vertical-slice ADR **for the planning bounded context only**)
**Context:** Planning has three writers by design — the human door, the agent door, and the CLI importer (`--import-backlog`) — which is exactly the extraction trigger of the "vertical-slice minimal APIs" ADR (a second write path for the same aggregate). Beyond duplication, every mutation must end with a materializer `SyncAsync` (disk follows DB per strategy); a per-handler convention could be silently forgotten on the next route, diverging disk from DB with no error.
**Decision:** `PlanningFeatureService` (`CreateAsync`/`UpdateAsync`/`DeleteAsync`/`ImportAsync`) and `PlanningArtifactService` (`UpsertAsync`/`SetStatusAsync`/`ValidateAsync`/`AppendLogAsync`/`DeleteAsync`) own the full mutation unit: load → domain method → `SaveChangesAsync` → materializer sync (swallow-and-log, so disk can never fail a DB write) → failure translation. `PlanningException`/`PlanningFailureKind`/`PlanningFailureCode` in `Core/Abstractions` is the single error vocabulary; `Host/Api/PlanningErrors.Map` is the only place it becomes HTTP. Shared persistence guards (unique-violation detection, swallow-and-log wrappers) live in `PlanningServiceGuard`; the `BacklogImporter` parses markdown only and writes exclusively through `PlanningFeatureService.ImportAsync`. API handlers stay thin: resolve, call a service, map the result.
**Alternatives considered:** Keep pure vertical slices and share a conflict helper — rejected: the importer would still re-implement upsert-by-slug/kind+order logic and the restore-vs-update rules, a second enforcement path in disguise. Move the ceremony behind a generic mediator/dispatcher — rejected: indirection with one aggregate and no cross-context reuse.
**Consequences:** This supersedes the vertical-slice ADR for planning only; Entries/Kits/Projects stay handler-direct under the original sanction. Any new planning write path (P2 tools, background jobs) must go through the services, not around them — encoded as a Don't in `STRUCTURE.md`. Same-shape contexts that later gain a second writer should follow this extraction rather than re-litigate it.

## Planning conventions: canonical version numbering and enum posture — 2026-09-13
**Status:** Accepted (records plan-006 amendment A5 and the 006/01b schema decisions; normative lines live in `STRUCTURE.md` rules 11–12)
**Context:** `PlanningArtifactVersion` needed a labelling rule and the six planning enums needed a persistence posture before the first migration shipped. `ContextEntry`/`EntryVersion` predate planning and start a fresh entry at version 0 — off by one against the rule planning wanted.
**Decision:** Canonical version numbering: a version row labelled N holds the body that was live at version N, and a fresh aggregate is version 1 — planning entities follow it; retrofitting `ContextEntry.UpdateContent`/`CurrentVersion` (touches `EntryApiTests`, `EntryMapper`, the web badge) is tracked as hardening in `BACKLOG.md`, not code inside 006. Enum posture: explicit values on all six planning enums, vocabulary enforced in the domain (`PlanningArtifact.AllowedStatuses(kind)`), no DB CHECK constraints — acceptable because the store is a trusted local SQLite file; a shared/server store would need the vocabulary re-enforced in the schema.
**Alternatives considered:** Adopt the entries' off-by-one numbering for symmetry — rejected: it makes every version query mental arithmetic. DB CHECK constraints for status vocabulary — rejected: duplicated vocabulary in schema and domain that must be kept in sync by hand, on a store that is local and single-writer.
**Consequences:** Two version grammars coexist until the hardening lands (planning N=live-at-N, entries N-1=live-at-N); UIs and tools must not assume one grammar covers both. Enum drift between domain and database is impossible by construction since only the domain checks.

## MCP adapter bypasses the system proxy on loopback — 2026-09-12
**Status:** Accepted
**Context:** A bare `new HttpClient()` honours the system proxy (`SocketsHttpHandler` default `UseProxy = true`). Measured on the dev machine (`audits/audit-2026-09-10.md`, BLOCKER-1): with a system proxy on `127.0.0.1:2080` and no bypass list, every MCP-adapter call to the Host at `127.0.0.1:4761` was routed through a third-party proxy process — breaking the "loopback is the security boundary" rule, producing `502 Bad Gateway` instead of "unreachable" when the Host is down, and making the Mcp contract suite environment-dependent (green with the proxy off, red with it on). Recorded 2026-09-12; the fix shipped 2026-09-10 (commit `7394389`).
**Decision:** `OvermindApiClient.CreateHttpClient` builds `new SocketsHttpHandler { UseProxy = false }` (`src/Overmind.Mcp/OvermindApiClient.cs:57`), with a comment in code stating why so it does not get "cleaned up". Scope is `Overmind.Mcp` only: Infrastructure embedding providers keep proxy support, because their base URLs (Ollama, OpenAI-compatible) may be remote.
**Alternatives considered:** Rely on the OS proxy bypass list (`ProxyOverride` / `no_proxy`) — rejected: it is machine configuration we neither own nor can verify at runtime. Bypass the proxy process-wide — rejected: embedding providers legitimately need the proxy for remote URLs.
**Consequences:** Loopback Host traffic never leaves the loopback regardless of system proxy state; the Mcp test suite is proxy-independent. The SPA side is not covered — browsers may still proxy `*.localhost` (see ADR "Browser URL is `overmind.localhost`" and the P0 check in `BACKLOG.md`).

## Browser URL is `overmind.localhost` — 2026-09-12
**Status:** Accepted
**Context:** The Host opens the SPA in the default browser at startup and on single-instance relaunch. Opening `http://127.0.0.1:<port>` works but is opaque in the tab bar/history and shares the browser's `127.0.0.1` origin jar (cookies, storage) with anything else bound there. `*.localhost` names resolve to loopback per RFC 6761 and via systemd-resolved/nss-myhostname on Ubuntu. Shipped as `BrowserUri.FromLoopback` (commit `66f51b8`); recorded here 2026-09-12 after the audit flagged it as untracked work.
**Decision:** `BrowserUri.FromLoopback` (`src/Overmind.Host/BrowserUri.cs`) rewrites the bound URL's host to `overmind.localhost` when it is `127.0.0.1`/`localhost`/`[::1]`, and leaves any non-loopback bind untouched. The rewrite is browser-facing only — Kestrel still binds `127.0.0.1`.
**Alternatives considered:** Open `127.0.0.1` directly — rejected: poorer UX and shared origin jar. Register a real local hostname / mDNS — rejected: platform-specific setup for a cosmetic gain.
**Consequences:** Works out of the box on Ubuntu (systemd-resolved) and Windows/macOS. Known caveats, accepted: minimal systems without nss-myhostname may not resolve `*.localhost` (fallback: browse to `http://127.0.0.1:<port>` from the port file); browsers behind a system proxy may proxy even `*.localhost` — tracked as the P0 manual check in `BACKLOG.md`.

## Frontend data access: React Query + same-origin fetch from a static-export SPA — 2026-09-07
**Status:** Accepted (supersedes the global Server-Actions/BFF default for this project)
**Context:** The global frontend conventions mandate Next.js Server Actions for mutations and forbid direct `fetch` from client components, routing everything through a Next.js backend (BFF). The MVP web UI is built with `output: "export"` and served as static files by the Kestrel host (spec R1.1/R7.1): in production there is no Next.js server at all, so Server Actions and route handlers are impossible by construction. Surfaced during the 001 hard architect review (`audits/architect-review-2026-09-07.md`) as an undocumented deviation.
**Decision:** All server access in `web/` goes through React Query (`useQuery`/`useMutation`) over the single `shared/api/client.ts` fetch wrapper, calling the same-origin `/api/*` of the hosting Kestrel process. The BFF role is filled by same-origin static hosting (the SPA and the API share origin, port, and loopback security boundary), not by Next.js server functions. Query-key factories stay centralized in `features/*/queries.ts`; no `useEffect` data fetching.
**Alternatives considered:** Run a Next.js server alongside Kestrel to enable Server Actions/BFF — rejected: a second runtime contradicts the single-process download-and-run product decision. Call the API via hand-rolled hooks without React Query — rejected: loses caching/invalidation discipline already established.
**Consequences:** The global Server-Actions rule does not apply to this repo. Anything requiring a Next server (SSR, route handlers, middleware) is off the table while the SPA is static-export. Navigation uses plain `<a href>` (the Next 16 static-export client router is broken upstream); revisit if upstream fixes land.

## Backend API layering: vertical-slice minimal APIs with EF Core in handlers — 2026-09-07
**Status:** Accepted
**Context:** Every Host endpoint module (`ProjectsApi`, `EntriesApi`, `KitsApi`, `SearchApi`, `SettingsApi`, `HealthApi`, `SystemApi`; later joined by `SystemRootsApi`, `PlanningFeaturesApi`, `PlanningArtifactsApi`) injects `OvermindDbContext` directly into minimal-API handlers, with validators and mappers beside them. This diverges from the global default ("split API/DTO/Service, Clean Architecture") but is consistent, well-tested, and proportionate for a single-write-path MVP. Recorded during the 001 hard architect review (`audits/architect-review-2026-09-07.md`, WARNING-2). Live size example: `KitsApi.cs` at 288 lines is the largest module and near the extraction trigger.
**Decision:** Sanction the vertical-slice style for v1: one static class per bounded context under `Host/Api/`, handlers own their EF queries, domain invariants live on entities where practical. **Extraction trigger:** (a) a second write path for the same aggregate appears (e.g. P2 MCP tools writing beyond note/decision/gate/guard, background reconcilers), or (b) any API module exceeds ~300 lines. On trigger, extract application services per bounded context, starting with kit activation (the single-active-kit invariant is endpoint-only today — review WARNING-1).
**Alternatives considered:** Extract application services now (Mediator/handlers per use case) — rejected: indirection without a second consumer at MVP size; the trigger-based rule defers the cost until a real force exists. Keep the style without an ADR — rejected: reviewers and agents need to know the pattern is intentional, not drift.
**Consequences:** New endpoints follow the existing slice pattern (contract + validator + mapper + handler). The single-active-kit invariant and similar endpoint-only rules must be re-enforced by any new write path until extracted. The ~300-line ceiling is checked at each architect review.
**Trigger update 2026-09-12:** The extraction trigger fired for the planning bounded context (006-planning, plan amendment A1): write paths in `PlanningFeaturesApi`/`PlanningArtifactsApi` delegate to application services extracted into `Infrastructure/Planning/` (`PlanningFeatureService`, `PlanningArtifactService`); the API modules keep direct `OvermindDbContext` reads for light lookups. Kit/context-entry slices remain direct-EF under the original sanction.

## Custom MCP resource scheme is `overmind://` — 2026-09-07
**Status:** Accepted (supersedes the original `ctx://` scheme decision from spec R2.2 era)
**Context:** The custom MCP resource URI scheme was originally `ctx://`. It is generic enough to collide with other MCP servers a user has installed, and does not identify the product. The rename window is ideal: MVP stage, no external consumers, and materialized agent instructions referencing the scheme live only in the user's own projects (re-materialization fixes drift).
**Decision:** The custom MCP resource URI scheme is `overmind://` (e.g. `overmind://projects/<id>/gates`). All code, tests, and docs reference the new scheme. Supersedes the original `ctx://` decision.
**Alternatives considered:** Keep `ctx://` — rejected: collision risk with third-party MCP servers, poor self-documentation. Use a registered IANA scheme — rejected: unnecessary for an in-process MCP resource identifier.
**Consequences:** Previously materialized bootstrap files referencing `ctx://` drift until re-materialization; no migration is shipped for the same reason (drift + re-materialization covers it).

## Single active kit per project — 2026-09-06
**Status:** Accepted
**Context:** The data model (`ProjectKit` many-to-many with `IsActive`) technically allows multiple active kits per project, but the materializer emits one `overmind-bootstrap/SKILL.md` per platform, so a second kit activation on the same platform collides (409 OverwriteBlocked). Surfaced during task 04 hard review (architect IMPORTANT-1). The frozen spec already implies switch semantics: "switching a kit re-materializes files".
**Decision:** Exactly one kit may be active per project. `Activate` with another kit already active returns 409 instructing to deactivate first; the UI offers a "switch" flow (deactivate + activate). No per-kit bootstrap namespacing.
**Alternatives considered:** Multi-kit with `overmind-bootstrap-<kit-slug>/` namespacing — rejected: bigger conflict/drift surface, marginal v1 value.
**Consequences:** Simpler materialization and UI. Revisiting multi-kit = new ADR + bootstrap namespacing work.

## Project DiskPath is immutable while a kit is active — 2026-09-06
**Status:** Accepted
**Context:** `MaterializedFile` rows store relative paths; dematerialize resolves them under the project's current `DiskPath`. Changing `DiskPath` while files are materialized would make deactivate delete foreign files at matching relative paths in the new directory (task 04 review, blocker B1).
**Decision:** `PUT /api/projects/{id}` rejects `DiskPath` changes with 409 while any kit is active or any `MaterializedFile` rows exist; the user deactivates kits first.
**Alternatives considered:** Persist absolute path snapshot per `MaterializedFile` and refuse deletes on mismatch — rejected for v1 as a heavier invariant (extra migration, snapshot semantics) where a state guard achieves the same safety.
**Consequences:** DiskPath retarget requires an explicit deactivate step — visible, safe, and self-explanatory via the 409 message.

## Host↔MCP contract is unversioned, additive-only — 2026-09-06
**Status:** Accepted
**Context:** The stdio MCP adapter deserializes Host API DTOs via tolerant `JsonElement` reads. Both ship from the same repo at the same version, but the bundled-installer feature (003) makes divergent deployments conceivable. Adapter writes are restricted to note/decision/gate/guard in v1 — skill entries carry files and are managed via UI until P2 runtime delivery.
**Decision:** The Host API contract consumed by the adapter evolves additive-only: new fields allowed, renames/removals forbidden. No version negotiation in v1.
**Alternatives considered:** Explicit contract versioning / shared contracts package — rejected for v1 as overhead in a single-repo, same-version ship.
**Consequences:** Renames in Host DTOs silently break the adapter (known hazard, tolerated while single-repo); revisit when 003 introduces separate distribution.
