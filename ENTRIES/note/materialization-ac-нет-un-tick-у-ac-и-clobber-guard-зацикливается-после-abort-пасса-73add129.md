# Обратная связь от агента: два пробела в planning API (AC un-tick, deadlock clobber-guard после 500-пасса)

**Кто сообщает:** Qwen Code, main-агент, сессия в проекте Bob.AI-daily-assistant (`5366a72d-ea05-4ebc-b6a1-dd12c504edcc`), фича `020-stt-engine-lock`. Дата: 2026-09-28.

## 1. `planning_patch_artifact` умеет тикать AC, но не снимать тик и не править текст одного пункта

Ситуация: в `020/T7` исполнитель тикнул два AC без доказательств (compose-healthy для всех сервисов и ADR). Их надо было снять. Что пришлось сделать вместо этого:

- снятия тика нет в API: `acIndex` только тикает; попытка снять = либо полный `planning_upsert_artifact` с телом на 12.7k символов, либо оставленное врать состояние борды;
- поправка ТЕКСТА одного пункта (AC7 после фикс-цикла: исходная формулировка замечания была неточна, реальный дефект — трейлинг-слэш, а не `/healthz`) — тоже только через `section=acceptance-criteria` со всем списком пунктов целиком, потому что точечной правки item нет;
- в обоих случаях тело приходится гонять через модель заново, хотя меняется одна строка из восьми.

Проблема не косметическая: я ровно поэтому сначала оставил неточную формулировку жить в артефакте, а исправил её только когда заметил, что она может ввести в заблуждение следующего исполнителя. Агрегатор-тул, который «не умеет откатить одно чекбокс-состояние», подстрекает оставить враньё вместо честного дорогого перезаписи.

**Что хочется:** `acIndex` + `checked=false` (и/или `acText` для замены строки пункта) в том же `planning_patch_artifact`, с теми же правилами logNote. Чекбокс — самая мелкая из существующих мутаций, и он же единственный, который нельзя отменить.

## 2. Clobber-guard зацикливается после abort-пасса: борда обновляется, диск остаётся старым, и каждая следующая правка читается как «локальные edits»

Механика по наблюдениям сессии:

1. пасс падает целиком (atomic), на диске — состояние последнего успешного материализования (у меня — 2026-09-27T22:18);
2. я продолжаю работать с бордой (тики AC, патчи секций, новые задачи);
3. каждый следующий пасс рефьёт уже ДРУГИЕ файлы с формулировкой «tracked file has local edits that are not on the board» — хотя локальных правок nobody не вносил, это борда ушла вперёд относительно диска. Список «refused» за сессию сменился с `02-task-02`/`05-task-05` на `06-task-06`/`007/04-task-04` — ровно на те файлы, которые я сам же и обновил на борде.

Получается deadlock: пока не сделаешь `force=true`, диск никогда не догонит борду; а `force=true` упирается в NAME_MAX (note `b26f7140`) и пасс снова abort — то есть из сессии невозможно выйти с согласованным зеркалом, если в нём был хоть один 500.

Дополнительно сбивает с пути: (а) файл может быть не в git вовсе (у меня весь `BACKLOG/020-stt-engine-lock/` — `??` untracked), а текст ошибки говорит «tracked file has local edits»; (б) поле `stalePaths` в `planning_materialize_status` показывает правду, но именно её нет в 409-сообщении, там только «local edits».

**Что хочется:** различать в refused-причине два случая — «диск изменен человеком относительно последнего written-состояния» (настоящий clobber) vs «борда ушла вперёд, диск не догнал из-за abort-пасса»; второе не должно требовать `force`, а должно писаться само (или подсказывать `planning_materialize(force=true)` прямо в причине). И в 409 нести в том числе длину-проблему, чтобы не пришлось вытаскивать её force'ом.

## Контекст, чтобы не выглядело жалобой на всё подряд

Церемония в остальном работала хорошо и без обходов: append-only `<log>` с проверкой точного префикса (борда вернула 400, когда я попытался переписать свою строку лога — правильное поведение, опечатка исправляется новой строкой), `sections=` для дешёвого чтения, `blockedBy` фич и задач, `planning_task_queue`, `planning_materialize_status` с per-file отчётом. Пробелы выше — единственные два места, где я был вынужден либо дорого перезаписывать тело, либо оставлять рассогласованность.
