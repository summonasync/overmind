# Materialization: имя файла из `brief` без length-guard ⇒ 500 и aborted-пасс на кириллице

**Кто сообщает:** Qwen Code, main-агент, сессия в проекте Squeezr (`31f33e30-6056-40a3-8447-c43d889fee9f`), фича `063-dogfood2-ignore-recall-suggest`. Дата: 2026-09-28.

## Что произошло

1. `planning_upsert_tasks` (6 задач) — принят бордой без жалоб: валидация `brief` = «one-line summary, max 500 chars», и мои брифы были в пределах 500 СИМВОЛОВ (например для order 1 — 236 симв.) 
2. Автоматическая материализация после мутации не случилась; `planning_materialize_status` показал `lastSuccess=11:35:49`, `lastAttempt=12:09:27` с abort на guarded-файле (не про то, см. ниже).
3. `planning_materialize(force=true)` → **HTTP 500**, и текст прямо говорит, что не лезет имя файла:
   ```
   File operation failed for '.../BACKLOG/063-.../tasks/01-ядро-исключений-рукописный-gitignore-матчер-...-не-трогаем.md':
   The path ... is too long, or a component of the specified path is too long.
   ```
4. Факт на диске: `BACKLOG/063-dogfood2-ignore-recall-suggest/tasks/` **пустой** — ни одной задачи, при этом feature.md/spec.md/plan.md от物料изировались нормально. То есть mirror для задач фичи молча отсутствует, а борда показывает «6 задач, статусы двигаются».

## Почему борда пропускает, а диск нет

Лимит 500 символов считается в СИМВОЛАХ, а ext4 NAME_MAX = 255 **байт** на компонент пути. Кириллица в UTF-8 = 2 байта/символ, плюс слагификация (транслит не нужен, пробелы→дефисы) — 236 симв. ≈ 400+ байт ⇒ ENAMETOOLONG. Для латиницы та же длина проходит: на диске живут файлы до 211 байт (`02-query-surface-code-search-kind-param-all-code-docs-default-all-...`), то есть запас до 255 небольшой даже на английском.

Второй момент: 500 на ОДНОМ имени роняет весь пасс, а не пропускает файл с warning'ом. Это не «guarded file» (там был аккуратный 409 со списком), а жёсткий отказ с частичной записью: feature/spec/plan уже на диске, tasks — нет.

## Какие проблемы это сделало

- Mirror 063 (6 задач, включая in-flight у трёх кодеров) не виден на диске → агенты без Overmind MCP и люди по AGENTS.md читают пустоту, и это молча выглядит как «фича без задач».
- Починка дорогая: `brief` меняется ТОЛЬКО через полный upsert с `body` (body required; planning_patch_artifact не умеет brief). То есть для косметики имени файла нужно перезалить 6 тел — а 3 задачи прямо сейчас читают/пилят исполнители, и re-upsert может сдвинуть версию/статус in-flight контракта. Я осознанно отложил перезалив до конца волны, а не сделал сразу.
- Формулировка 409 про «local edits that are not on the board» вела по ложному следу: истинная причина 500 — длина имени, но чтобы это увидеть, нужен был именно force-прогон.

## Что хочется

- Валидировать `brief` при записи НЕ по 500 символам, а по budget'у имени файла (UTF-8 NAME_MAX минус запас на `NN-` и `.md`), с понятной ошибкой на write-time: «brief too long to materialize, N bytes > M».
- Либо резать slug детерминированно (первые N байт + детерминированный суффикс), чтобы материализация никогда не падала по имени.
- Либо отдельный short slug-field для имени файла, не производный от длинного brief.
- Либо в 409 про guarded files нести и длину-проблему, чтобы не пришлось force'ом вытаскивать настоящую причину.

## Временный порядок в Squeezr (чтобы не наступать снова)

Короткие `brief` на английском (как в 057/060/062), длинные детали — в `<goal>`/`<scope>` тела задачи. Мои русские брифы в 063 будут перезаписаны английскими по завершении волны (статусы 3 in-flight задач не хочу дёргать mid-flight).
